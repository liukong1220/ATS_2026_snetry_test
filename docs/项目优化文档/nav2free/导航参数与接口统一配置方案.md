# 自研导航参数与接口统一配置方案

更新时间：2026-08-02。

目标是让正式自研入口继续使用原路径 `src/ats_sentry_bringup/params/node_params.yaml`，
用户可以直接在原参数文件中修改和删除参数；不新增第二个“Nav2-free YAML”。YAML
只描述节点连接和运行参数，`.msg/.srv/.action` 才是接口字段和常量的 schema 权威。

## 1. 当前结论

| 项目 | 当前状态 | 下一步 |
| --- | --- | --- |
| ROGMap、adapter、MINCO、Goal Manager、MPC 段 | 已在 `node_params.yaml` | 删除同名 Nav2 段和私有覆盖 |
| behavior 参数 | 默认仍从 `ats_sentry_behavior/params/sentry_behavior.yaml` 加载 | 合并正式段并让 bringup 只传总 YAML |
| ROGMap core | wrapper 参数在总 YAML，core 仍可读取 `map_config_file` | 增加显式 ROS parameter struct 构造并禁止双来源 |
| Nav2 参数 | `bt_navigator`、costmap、planner/controller 等仍在总 YAML | 运行入口切换后删除 |
| planning grid owner | `rc_esdf|rog_map` 可选 | 最终固定 `rog_map`，删除运行时热切换 |
| 速度兼容层 | fake-yaw/chassis 参数独立于 Nav2，实机默认 true | 去掉参数名和 topic 中的 Nav2 语义 |

当前不能写“单 YAML 已完成”，只能写“自研核心节点已经汇总，纯自研单一权威尚未闭合”。

## 2. 单一权威规则

1. 正式实机所有活动节点只接收同一个 `node_params.yaml`。
2. launch 只覆盖 `use_sim_time`、地图/PCD/设备路径和受控 HIL 开关。
3. 几何、动力学、topic、frame、QoS、timeout、unknown 和安全阈值不得由 launch 隐式覆盖。
4. MuJoCo 可以有独立仿真总 YAML，但必须明确是仿真 profile，不能与实机参数拼装。
5. 迁移期间的 package YAML 只能作为镜像对照；未通过 effective parameter dump 前不得删除。
6. `planning_grid_owner` 最终固定 `rog_map`，不允许运行中热切换。
7. 禁止 YAML anchor/alias 作为运行契约；重复 topic/frame 必须由 validator 校验一致。

`smoother_server`、`waypoint_follower`、`velocity_smoother`。

## 4. ROGMap 参数迁移

当前 `AtsRogMapNode` 仍把核心配置文件交给自定义 loader。正确迁移顺序：

1. 为现有 `rog_map::Config` 的每个运行字段建立参数 schema，保留原默认值和单位；
2. 在 ROS wrapper 中声明参数，在 core 中增加显式 struct 构造入口；
3. 用旧文件和新参数构造同一 Config，逐字段比较 resolution、map size、raycast、
   inflation、ESDF、stale decay、height band 和 unknown 语义；
4. 正式 profile 禁止同时设置 `map_config_file` 和显式参数；
5. 通过 validator、单测和 `ros2 param dump` 后删除正式 launch 对私有 map YAML 的引用。

以下字段必须保留语义，不能只改名字：

```yaml
ats_rog_map:
  ros__parameters:
    map_frame: odom
    base_frame: gimbal_yaw_odom
    sensor_frame: front_mid360
    odom_topic: /localization
    cloud_topic: /registered_scan
    cloud_timeout_sec: 2.0
    odom_timeout_sec: 2.0
    tf_timeout_sec: 0.1
    debug_bounds_topic: /rog_map/bounds
    esdf_visualization_height: 0.15
```

ROGMap 的 `/rog_map/occ`、`/rog_map/inf_occ`、`/rog_map/unk`、`/rog_map/esdf` 和
`/rog_map/bounds` 是诊断输出，不是 planner 的数值输入。

## 5. 当前接口账本

| 接口 | 类型 | producer | consumer | 当前状态/限制 |
| --- | --- | --- | --- | --- |
| `/localization` | `nav_msgs/msg/Odometry` | localization fusion/Point-LIO profile | ROGMap、Goal Manager、MPC | 已接；观测 stamp、frame 和 stale 需实机测量 |
| `/localization/status` | `LocalizationStatus` | localization fusion | adapter、Goal Manager、MPC | 已接；epoch 与健康状态有效 |
| `/registered_scan` | `sensor_msgs/msg/PointCloud2` | Point-LIO 链 | ROGMap | 已接；过期触发 stale |
| `/rog_map/get_ground_projection` | `GetRogMapProjection.srv` | ROGMap | adapter | 已接；同一 response 含 grid、SDF、gradient、generation、ready/stale |
| `/rc_esdf/planning_grid` | `nav_msgs/msg/OccupancyGrid` | adapter 或旧 RC-ESDF 二选一 | JPS/行为 | 已接但 owner 可选；最终固定 adapter |
| `/rog_map_adapter/status` | `PlanningMapStatus` | adapter | Goal Manager/诊断 | 已接；grid 与 status 仍非同一消息 |
| `/ats_navigate_to_pose` | `NavigateToPose.action` | Goal Manager | behavior/RViz/test | 已接；feedback/result/cancel/preempt/timeout |
| `/ats_goal_manager/planner_goal` | `PlannerGoal.msg` | Goal Manager | MINCO | 已接；`goal_id` 无 restart incarnation |
| `/minco/planning_status` | `PlannerStatus.msg` | MINCO | Goal Manager | 已接；与 candidate reference 分 topic |
| `/minco/reference_path_candidate` | `nav_msgs/msg/Path` | MINCO | Goal Manager | 已接；Path 不是完整 candidate schema |
| `/planner/execution_command` | `ExecutionCommand.msg` | Goal Manager | MPC/serial gate | 部分完成；reference、授权和 `manager_incarnation` 同一消息，MPC 强制新实例 STOP 交接；serial 与 digest 未覆盖 |
| `/cmd_vel_mpc` | `geometry_msgs/msg/Twist` | MPC | fake-yaw/chassis | 已接；车体系 `[vx,vy,wz]` |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | chassis transform | serial bridge | 已接；必须单一 publisher |
| `/motion_control` | `ats_rm_interfaces` message | MuJoCo bridge | MuJoCo | 已接；必须单一桥和单一 subscriber |

目标接口 `PlanningMapSnapshot.msg`、`PlannerCandidate.msg` 和全链
`authority_incarnation` 授权消息尚不存在。`ExecutionCommand.manager_incarnation` 仅覆盖
Goal Manager -> MPC；下一轮扩展到其它 producer/consumer 前必须读取现有 message 和 QoS，
不得用多个 topic 名字拼成“原子消息”。

## 6. frame、time、QoS 和安全约束

| 契约 | 正式约定 |
| --- | --- |
| goal frame | action goal 初始为 `map`，Goal Manager 变换到 planning `odom` |
| robot frame | `gimbal_yaw_odom`，footprint `0.70 x 0.55 m + margin` |
| state | 世界系 `[x,y,yaw]` |
| command | 车体系 `[vx,vy,wz]`，不丢弃 `vy` |
| observation time | 传感器/里程计 stamp；TF 按观测时间查询 |
| deadline/lease | steady clock；ROS/sim time 只承载观测和消息时间 |
| unknown | 全来源无证据才输出 unknown，默认按障碍 |
| planning snapshot | 单次规划内 JPS、MINCO clearance、footprint gate/repair 共用 immutable snapshot |
| fallback | stale、timeout、无路、unsafe、MPC/执行失败 -> STOP、零速度 |
| velocity owner | MPC -> compatibility -> serial/MuJoCo 唯一执行桥 |

fake-yaw 和 chassis transform 是 frame 兼容层，不是 Nav2 组件。实机默认开启两者；
关闭 fake-yaw 时仍发布 `gimbal_yaw_odom -> gimbal_yaw_fake` 零旋转 TF，禁止增加
第二个 `base_footprint -> base_link` owner。

## 7. 参数迁移执行顺序

### U0：effective 参数清单

对 ROGMap、adapter、MINCO、Goal Manager、MPC、behavior、serial 和 transform 分别执行
`ros2 param dump`，记录实际加载文件、节点名、topic、frame、QoS、timeout 和默认值。

### U1：镜像与校验

只把已确认字段镜像到总 YAML，新增 validator 检查：

- 必需自研节点段存在，Nav2 段不存在；
- producer/consumer topic、frame、timeout 一致；
- `dt == 1/control_rate_hz`；
- `T_hold < T_cmd_watchdog <= T_execution_lease`；
- footprint、unknown、signed distance、planning resolution 一致；
- planning grid、`/cmd_vel`、`/motion_control` owner 唯一；
- `use_sim_time`、`require_*_status` 符合 profile；
- 正式 fake/chassis transform 默认启用。

### U2：逐节点切换

顺序固定为 adapter -> ROGMap -> MINCO -> Goal Manager -> MPC -> serial -> behavior。
每切换一个节点都运行包级单测、launch `--show-args` 和 effective param dump 对比。

### U3：删除第二来源

只有三方值一致且目标 launch 已只加载总 YAML 后，才能删除或改名 package 私有 YAML。
独立示例必须命名为 `example`，并在 launch/package 中证明不会被正式入口加载。

## 8. 停止条件

- 新参数改变 ROGMap occupancy、unknown、signed distance 或 inflation 语义；
- core 同时读取文件和 ROS 参数；
- launch 同时加载总 YAML 和私有 YAML；
- validator、effective dump 和源码默认值无法对齐；
- 新接口要求从 `/rog_map/esdf` 点云恢复数值；
- stale/unknown/unreachable/unsafe 后底盘非零；
- 为通过编译而删除仍被 MINCO 使用的 RC-ESDF provider。
