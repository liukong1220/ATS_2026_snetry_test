# 视觉跟随仿真调试

## 1. 文档定位

本文只讨论当前仓库内已经可用的 loopback 视觉跟随调试链路，目标是帮助你快速回答四个问题：

1. fake vision 是否真的把 `VisionTargetMsg` 发出来了。
2. 行为树是否真的进入了视觉接管分支。
3. `SelectVisionFollowPath` 是否真的生成了跟随路径。
4. 视觉失效后，系统是否真的回退到普通决策分支。

如果你想看更完整的行为树结构，请配合阅读：

- [`./sentry_bt_decision_checklist.md`](./sentry_bt_decision_checklist.md)

如果你想确认视觉接管触发 `attack` 姿态、低血量 `defend` 姿态和受击自旋的当前规则，请同时阅读：

- [`./sentry_posture_switch_logic.md`](./sentry_posture_switch_logic.md)

如果你想看视觉消息和路径生成原理，请配合阅读：

- [`./融合.md`](./融合.md)

## 3. 当前视觉跟随链路到底是什么

当前 loopback 里的视觉接管链路可以直接理解成：

```text
fake_decision_sim_inputs.py
  -> 发布 /vision/target
  -> behavior server 写入黑板 sp_vision_target
  -> IsVisionTargetValid
  -> PublishGimbalAbsolute
  -> SelectVisionFollowPath
  -> SendNavThroughPoses
  -> Nav2 + MPPI 执行
```

当前最关键的输入不是旧的目标索引，而是：

- `target_position_map`
- `has_target_position_map`
- `target_position_map_frame`

这意味着当前视觉跟随已经是“地图级目标点驱动”，而不是“给定固定点编号驱动”。

另外，当前版本已经把视觉接管策略改成了“平滑抢占”：

1. 视觉分支仍然可以抢占主树。
2. 但初次接管要经过 `activation_hold_s` 稳定窗口。
3. 目标切换要经过 `switch_target_hold_s` 稳定窗口。
4. 短时丢目标会在 `override_hold_s` 内保持。
5. 若当前血量低到需要回防，则视觉分支会主动让权给 retreat / safe_point。
6. 若只是刚补给恢复到低血量阈值附近，也不会立刻重新抢占，因为现在还增加了血量释放阈值迟滞。

## 6. 运行中最常用的检查项

### 6.1 先看 fake vision 是否真的在发

```bash
ros2 topic echo --once /vision/target
```

重点检查：

1. `tracking: true`
2. `nav_hold: true`
3. `has_target_position_map: true`
4. `target_position_map_frame: map`
5. `target_position_map` 是有限值

注意：

- 当前代码并不会因为 `target_position_map = 0,0,0` 就自动判它无效
- 真正的必要条件是 `has_target_position_map=true`、frame 非空且点是有限值

ros2 param set /fake_decision_sim_inputs vision_target_position_map_x 2.5

## 6.4 为什么会出现“快到终点就反向试探”

这个现象不能简单理解成 “MPPI 不行”。

当前工程里，局部控制是否稳定，至少同时受三层影响：

1. 行为树是否在高频改发新的局部目标点。
2. `SelectVisionFollowPath` 是否在敌方目标周围频繁换侧。
3. MPPI 是否在当前局部目标、障碍分布和速度约束下还能给出平滑解。

本项目这次遇到的典型症状是：

1. 机器人靠近攻击半径边界后，当前车体相对敌人的方位角会快速变化。
2. 如果 `SelectVisionFollowPath` 每次都按“当前相对方位”重新选采样主方向，
   跟随点就可能从目标左侧突然翻到右侧。
3. Nav2 收到的是两个互相矛盾但都“看起来合法”的短路径。
4. MPPI 于是表现成转角前后反复试探、局部轨迹乱飘、甚至短暂反方向规划。

除此之外，还有一个很容易被忽略的放大链路：

1. 即使上层视觉跟随点只是在旧目标附近小幅漂移。
2. 如果 `SendNavThroughPoses` 每次都立刻 cancel 当前 goal 再重发。
3. Nav2 / MPPI 就会把这些本来不大的扰动当成“新的强制意图切换”。
4. 于是近终点、角点、窄路口的局部预测会更容易左右抽动。

为此，代码中新增了两项稳定参数：

- `decision.vision.prefer_previous_goal_side`
  含义：若上一帧已经选出稳定可行的跟随侧，则优先继续沿用这一侧。
- `decision.vision.max_target_shift_for_side_hold_m`
  含义：只有当敌方地图点变化不大时，才继续沿用旧侧；若敌方确实大幅移动，再允许重新选侧。
- `decision.decision_config.active_goal_hold_tolerance`
  含义：若新 path 与当前已经发给 Nav2 的 path 只在小范围内不同，则先保持当前 goal，不急着抢占。
- `decision.decision_config.active_goal_min_resend_interval_s`
  含义：即使 path 有轻微变化，也要求与上一次发 goal 至少间隔这么久，才允许再次重发。

推荐理解方式：

1. `attack_radius` 决定“绕敌人多远”。
2. `follow_arc_half_angle_deg` 决定“允许在敌人周围多大角域里找点”。
3. `min_replan_interval_s` 和 `min_goal_shift_m` 决定“多久、偏多少才值得重发新点”。
4. `prefer_previous_goal_side` 和 `max_target_shift_for_side_hold_m` 决定“不要轻易从这一侧翻到另一侧”。
5. `active_goal_hold_tolerance` 和 `active_goal_min_resend_interval_s` 决定“即便上层新给了近似目标，也不要立刻抢占正在执行的 Nav2 goal”。

如果你看到的是：

- 跟随点总贴角点左右乱跳：先检查 `prefer_previous_goal_side` 是否为 `true`
- 目标稍微横移机器人就仍死守旧侧：适度减小 `max_target_shift_for_side_hold_m`
- 仍然重规划过于频繁：再继续调大 `min_replan_interval_s` 或 `min_goal_shift_m`
- 上层看起来已经稳定，但 Nav2 仍频繁被新目标打断：继续调大 `active_goal_hold_tolerance`
- 快到终点或转角仍会来回抢占：继续调大 `active_goal_min_resend_interval_s`
- `decision.vision.override_hold_s`
- `decision.resource_policy.defend_enter_hp`
- `decision.resource_policy.defend_exit_hp`
- `decision.resource_policy.resupply_enter_hp`
- `decision.resource_policy.resupply_exit_hp`
- `decision.resource_policy.resupply_enter_ammo`
- `decision.resource_policy.resupply_exit_ammo`

其中血量相关两个参数要配套理解：

1. 当前是否允许视觉接管，不再由视觉节点自己读血量阈值，而是由统一资源状态机决定。
2. `defend_enter_hp / defend_exit_hp` 控制“极低血量退防”进入与退出阈值。
3. `resupply_enter_hp / resupply_exit_hp` 控制“回补给安全点”进入与退出阈值。
4. `resupply_enter_ammo / resupply_exit_ammo` 控制“低弹量停止追击并回补”进入与退出阈值。
5. 所有 `exit` 一般都应高于对应 `enter`，差值越大，切换越稳，但恢复追击会更慢。

### 6.4 验证视觉失效后的回退

```bash
ros2 param set /fake_decision_sim_inputs vision_tracking false
```

或者：

```bash
ros2 param set /fake_decision_sim_inputs publish_vision_target false
```

预期现象：

1. `IsVisionTargetValid` 失败
2. `vision_test` 下会回退到 `decision_simulation`
3. `rmul_2026` 下会回退到 simulation 或 referee 分支

如果只是短时遮挡或一两帧消息抖动，则不一定会立刻回退，这是当前设计的预期行为。
因为 `override_hold_s` 本来就是专门用来吸收这类短时扰动的。

## 7. 当前 RViz 里应该看什么

当前推荐重点观察：

1. `/decision/vision_follow_markers`
2. 全局路径
3. 局部轨迹 / trajectories
4. 机器人当前位姿
5. `/odom` 与 TF 是否持续更新

当前 `SelectVisionFollowPath` 会发布的 marker 语义是：

1. 红点：视觉目标地图点
2. 青色弧线：围绕目标的候选跟随圆弧
3. 绿色点：最终选中的跟随点
4. 黄色线：当前位姿到跟随点的连线

注意：

- 当前代码中真正持续发布的是 `decision/vision_follow_markers`
- 不要把 RViz 里历史残留的 `vision/target_point_map` 显示项当成当前主观察来源
- 如果你在 loopback 里手动改了机器人位姿，`decision_current_pose` 现在会优先尝试用 TF 兜底刷新
- 因此即使 `/odom` 更新短暂停滞，也不应该再像旧版本那样因为 `pose stale` 直接卡死

## 8. 当前日志应该怎么理解

### 8.1 看到 `Vision follow target=(...) selected_goal=(...)`

表示：

1. 视觉目标有效
2. 当前位姿有效
3. `SelectVisionFollowPath` 成功选出了一个跟随点

### 8.2 看到 `Send NavigateThroughPoses goal with 1 poses`

表示：

1. 当前视觉分支生成的是单点 path
2. 该 path 已经被发给 Nav2

这是正常现象，不是“少发了 waypoint”。

### 8.3 没有反复看到发送日志，不代表没工作

`SendNavThroughPoses` 现在有“同一路径不重发”的逻辑。

并且当前又多了一层：

- “近似同目标也先不急着抢占”的逻辑

所以当：

1. 视觉目标没变
2. 跟随点没明显变化
3. 当前 goal 仍在执行
4. 即使有轻微变化，但还在 `active_goal_hold_tolerance` 与 `active_goal_min_resend_interval_s` 的保护范围内

你可能不会每个 tick 都看到新发 goal 的日志，这恰恰说明节流与去重在工作。

### 8.4 到点判定现在怎么工作

当前 `IsPathGoalReached` 的逻辑是：

1. 如果输入端口里已经有 `goal_succeeded`，优先使用它
2. 否则再退回到几何距离判定

这意味着：

- 在 `vision_test` 和当前主树里，若 Nav2 已明确返回成功，行为树会优先相信 action 结果

## 9. 当前最常见的误区

### 9.1 误区一：视觉目标在发，行为树就一定会接管

不是。

还必须同时满足：

1. `tracking = true`
2. 若要求接管，则 `nav_hold = true`
3. 时间戳没超时
4. `target_yaw / target_pitch` 有效

### 9.2 误区二：目标点一变，就应该立刻重发路径

不是。

当前还有两层节流：

1. `min_replan_interval_s`
2. `min_goal_shift_m`

以及下一层 Nav2 入口节流：

3. `active_goal_hold_tolerance`
4. `active_goal_min_resend_interval_s`

如果变化太小，系统会复用旧路径，这是当前设计的一部分。

### 9.3 误区三：普通巡逻回退后一定会出现 `2 poses`

不是。

当前巡逻逻辑已经把 `patrol_preview_points` 实际钳制成单目标点发送，因此普通巡逻回退后，日志里依然很可能看到：

- `Send NavigateThroughPoses goal with 1 poses`

### 9.4 误区四：只要点是零值就一定无效

不是。

当前真正决定可不可用的条件是：

1. `has_target_position_map`
2. `target_position_map_frame`
3. 点是否有限
4. TF 是否可变换
5. 当前位姿是否可用

## 10. 推荐排查顺序

建议按这条顺序排查：

1. `ros2 topic echo --once /vision/target`
2. `ros2 action info /navigate_through_poses`
3. 看 `SelectVisionFollowPath` 日志
4. 看 `Send NavigateThroughPoses goal with 1 poses` 日志
5. 看 RViz 里的 `decision/vision_follow_markers`
6. 最后再去调视觉参数和 MPPI 参数

这样能把问题切开：

1. 消息没发出来，是输入层问题
2. 消息发出来但不接管，是条件层问题
3. 接管了但不出 path，是选点/TF/costmap 问题
4. path 出来了但车走得差，是 Nav2 / MPPI 问题

---

## 11. 一句话总结

当前视觉仿真调试最重要的三个抓手是：

1. `vision/target` 是否满足接管条件
2. `SelectVisionFollowPath` 是否成功生成单点跟随 path
3. `decision/vision_follow_markers` 和 `NavigateThroughPoses` 是否与日志一致

只要这三层对上了，后续再调的就是参数，而不是链路有没有打通。
