# ATS 导航代码框架优化方向与验证状态

## 当前闭环边界

当前 Gazebo 入口 `rmu_gazebo_simulator/ats_gazebo_nav.launch.py` 已将仿真域接入自研导航主线：

```text
Gazebo 传感器/真值
 -> /odometry、/registered_scan
 -> localization_fusion
 -> ROGMap + ground projection adapter
 -> JPS/A* + MINCO + 足迹安全门禁
 -> ats_swerve_mpc
 -> cmd_vel_arbiter
 -> gz_chassis_cmd_adapter
 -> MotionCtrl + Gazebo chassis Twist
```

`planning_grid_owner` 是启动时选择的唯一规划栅格 owner：`rog_map` 启动 adapter 并抑制 `rc_esdf_map`，
`rc_esdf` 走反向选择。Gazebo 默认使用真值里程计/点云中继；将
`use_gazebo_gt_odometry:=false` 才会启动 Point-LIO/LIO 兼容链。两种模式都保持下游 topic、frame
和急停契约不变。

## P3/P4 未完成项

- P3 仍需在 `launch_nav2:=false` 下证明无 Nav2 server、目标入口不调用 `NavigateToPose`，并通过扩大矩形与红框。
- P2 红框应记录终点坐标、位置误差、规划/reference 点数、离散足迹冲突数、失败/恢复次数；没有独立

- P4 的连续 swept footprint、实车动力学约束和实车运行尚未验证。

## 推荐验证顺序

1. 先运行 `python3 scripts/validate_navigation_config.py`、日志契约、Gazebo runner contract 和三仓库 `git diff --check`；
2. 在新 `ROS_DOMAIN_ID` 下运行无 GUI Gazebo 接口启动，检查 `/odometry`、`/registered_scan`、`/localization`、
   `/localization/status` 与 TF 的 producer/consumer 数量；
3. 使用 `PLANNING_GRID_OWNER=rog_map P2_FAULT_CASE=none TEST_PROFILE=red_box GOAL_TIMEOUT=300`
   运行 `scripts/test_mujoco_minco_mpc_chain.sh`，再为 Gazebo 增加同等 owner/fault 入口；
4. 最后分别注入 adapter lease、projection timeout、点云 stale、unknown 和 unreachable，确认
   `ready=false -> emergency_stop=true -> cmd_vel=0 -> motion_control=0`，恢复后旧 reference 不复活。

## 性能与日志口径

当前只记录本机实际运行结果，不把参考项目的 50 Hz、6 ms 或内存数据写成 ATS 实测性能。高频诊断使用
`RCLCPP_*_THROTTLE`，结构化键 `planned generation=`、`jps failed:` 和
`TRACE execution_command` 保留给自动化脚本；候选 CSV 继续逐候选写盘，避免把文本日志当作遥测通道。
