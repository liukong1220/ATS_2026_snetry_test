# 实机视觉跟随现状说明

这份文档只描述当前仓库中真实在使用的实机视觉接管链路。

## 1. 当前实机链路

当前实机视觉跟随主线可以直接理解成：

```text
sp_vision25
  -> 发布 vision/target (VisionTargetMsg)
  -> 包含 target_position_map / tracking / nav_hold / yaw / pitch

pb2025_sentry_behavior
  -> IsVisionTargetValid
  -> IsRobotResourceMode(state=engage)
  -> PublishRobotMode(mode=attack)
  -> PublishGimbalAbsolute
  -> SelectVisionFollowPath
  -> SendNavThroughPoses

Nav2
  -> SmacPlannerHybrid
  -> Nav2BSplineSmoother
  -> MPPI
  -> trajectory_speed_governor
  -> velocity_smoother
  -> cmd_vel_nav2_result
  -> fake_vel_transform
  -> /cmd_vel

standard_robot_pp_ros2
  -> /cmd_vel -> speed_vector
  -> decision/robot_mode -> speed_vector.mode
```

## 3. 当前视觉接管的必要条件

当前视觉接管不是“只要有目标就接管”，而是必须同时满足：

1. `IsRobotResourceMode(state="engage")`
2. `IsVisionTargetValid(...)`
3. `tracking=true`
4. `nav_hold=true`
5. 消息未超时
6. `target_position_map` 有效

如果这些条件有任意一项不成立，系统就会回退到普通分支，而不是保持 `attack`。

## 4. 当前真正驱动导航的视觉字段

当前真正驱动视觉跟随路径的是：

- `target_position_map`
- `has_target_position_map`
- `target_position_map_frame`

当前并不是只靠：

- `target_position_gimbal`
- `yaw`
- `pitch`

其中：

- `yaw / pitch` 主要给云台姿态使用
- `target_position_map` 才是导航跟随点计算的基础

## 5. 当前攻击圆周跟随的实现

当前行为层实现位置：

- [../src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp](../src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp)

当前逻辑：

1. 根据当前车位和敌方地图点，先求攻击圆周上最近点
2. 结合 costmap、边界余量、局部可通行性筛选候选点
3. 对选中点做角度限幅平滑
4. 位姿重定位或跳变时可清缓存后重选

因此现在的目标不是“死跟一个固定点”，而是“持续跟随攻击半径上最合理的点”。

## 6. 当前实机与 loopback 的关系

共用部分：

- 视觉接管判定
- 姿态切换
- 资源模式状态机
- 视觉圆周点选择
- `SendNavThroughPoses` 目标重发节流

不同部分：

- 实机使用真实视觉输入和真实裁判系统
- loopback 使用 `fake_decision_sim_inputs.py`
- 实机 Nav2 参数和 loopback Nav2 参数分离维护

## 8. 当前实机链路检查建议

### 8.1 先确认视觉消息

优先检查：

- `vision/target`

重点看：

1. `tracking`
2. `nav_hold`
3. `target_position_map`
4. `has_target_position_map`
5. `target_position_map_frame`

### 8.2 再确认行为层日志

重点看：

- `Decision resource mode=...`
- `Robot posture switched: ...`
- `Vision follow target=(...) nearest_ring_goal=(...) selected_goal=(...)`

### 8.3 再确认下位机接口

重点看：

1. `/decision/robot_mode` 是否变化
2. `/cmd_vel.angular.z` 是否在受击时变化
3. `standard_robot_pp_ros2` 是否正常把两者写入串口结构体

## 9. 当前实车链路的关键结论

### 9.1 `attack` 姿态

当前只要视觉接管成立，就会发布 `attack=1` 到：

- `decision/robot_mode`

最终下位机可以按 `int32_t mode` 或等价枚举接收。

### 9.2 自旋速度

当前自旋速度最终通过：

- `/cmd_vel.angular.z`

进入串口层，并写入：

- `SendRobotCmdData.data.speed_vector.wz`

### 9.3 模式与速度是两条独立信号

也就是说当前下位机接收时应把：

1. `mode`
2. `vx / vy / wz`

当成两条独立但协同的控制信息处理。

## 10. 本次 `/cmd_vel.linear.x/y = 0` 的排查结论

这次现象不是单纯“MPPI 没出速度”，更高概率是视觉接管前面的门控没有通过，导致行为树没有持续给 Nav2 下发有效视觉跟随目标，最终看到 `/cmd_vel.linear.x = 0`、`/cmd_vel.linear.y = 0`。

结合当前仓库代码，最常见的两个触发点是：

1. `vision/target` 虽然已经识别到目标，但 `nav_hold=false`
2. 行为树资源门控没有通过，`IsRobotResourceMode(state="engage")` 失败

### 10.1 为什么识别到目标了，`/cmd_vel` 还是 0

当前 `sentry_debug` 发出的不是底盘速度，而是：

- `tracking`
- `nav_hold`
- `target_yaw / target_pitch`
- `target_position_gimbal`

真正驱动导航接管的不是 `yaw/pitch`，而是 `target_position_map`。

也就是说：

1. `sentry_debug` 识别到目标
2. `Publish2Nav` 尝试把 `target_position_gimbal` 投到 `map`
3. 只有得到 `target_position_map` 且 `nav_hold=true`
4. 行为树才会进入 `SelectVisionFollowPath -> SendNavThroughPoses`
5. Nav2 才会继续输出非零 `/cmd_vel`

如果第 2 步 TF 失败、TF 过期、地图点无效，或者第 3 步 `nav_hold` 被压成 `false`，行为树就会拒绝视觉接管。

### 10.2 代码里真正会把视觉接管拦住的地方

`Publish2Nav` 内部并不会无条件保留 `nav_hold`，而是会再次检查：

- `tracking == true`
- `has_target_position_map == true`
- `confidence >= nav_hold_min_confidence`

只要这三项里有一项不满足，最终发布到 `vision/target` 的 `nav_hold` 就会变成 `false`。

随后行为树里的 `IsVisionTargetValid(require_nav_hold=true)` 会直接拒绝该目标。

### 10.3 为什么实机专测时也可能被主树清零

当前正式主树 `rmul_2026` 的视觉接管前，还要求：

1. `IsRobotResourceMode(state="engage")`
2. 裁判系统 `robot_status` 可用并且血量/弹量满足 engage

如果你现在是在实机上只开了 `sentry_debug` 做专测，但裁判系统链路没准备好，行为树就可能因为 `robot_status` 缺失而不允许进入视觉接管。

这种情况下你会看到：

- `vision/target` 有更新
- 云台也可能在动
- 但底盘视觉跟随没有真正进入导航
- `/cmd_vel.linear.x/y` 长时间保持 0

### 10.4 这次已做的优化

为了让视觉专测和实机短时抖动场景更稳，这次做了两项收敛：

1. `Publish2Nav` 增加了 `target_position_map` 短时缓存
2. `vision_test` 参数增加了“裁判状态缺失时临时按 engage 处理”的开关

第一项的目的：

- 当 `gimbal_yaw -> map` 的 TF 短时抖动或瞬时过期时
- 不要立刻把 `has_target_position_map` 打成 `false`
- 而是在很短时间内复用最近一次有效地图点
- 这样能减少 `nav_hold` 抖动导致的视觉接管反复掉线

当前新增参数：

- `vision_fusion.target_point_map_hold_s`

默认已在 `src/sp_vision25/configs/sentry.yaml` 中设为：

- `0.35`

第二项的目的：

- 让 `vision_test`/专测场景在没有裁判状态时也能跑通视觉跟随主链路
- 避免“明明识别到了敌人，但资源门控没过，主树一直不给底盘跟随”

当前新增参数：

- `decision.resource_policy.assume_engage_when_status_missing`

默认只在：

- `src/pb2025_sentry_behavior/params/sentry_behavior_vision_test.yaml`

中开启为 `true`，不会直接改变正式比赛主树的默认行为。

## 11. 现在上车时建议这样看

如果再次出现 `/cmd_vel.linear.x/y = 0`，按这个顺序看最快：

1. `ros2 topic echo /vision/target`
2. 看 `tracking`
3. 看 `nav_hold`
4. 看 `has_target_position_map`
5. 看 `target_position_map_frame`
6. 看行为树日志里是否出现 `Vision override rejected: nav_hold=false`
7. 看是否出现 `Decision resource mode=... expected=engage`
8. 看是否出现 `Vision follow target=(...)`
9. 看是否出现 `Send NavigateThroughPoses goal with ...`

如果：

- 有 `Vision follow target=(...)`
- 有 `Send NavigateThroughPoses goal with ...`
- 但 `/cmd_vel` 仍然是 0

这时再往下继续查 MPPI、`trajectory_speed_governor`、`velocity_smoother` 更有意义。
