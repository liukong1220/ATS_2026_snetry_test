这份文档不再只是“准备怎么改”的方案草稿，而是结合本次已经完成的代码修改，整理成一份可以直接学习的技术说明。

## 2. 最终想解决的核心问题

“真正的视觉跟随”不是只有云台在看目标，而是要让整条链路变成：

```text
视觉识别到敌方目标
-> 得到目标相对云台的三维位置
-> 利用机器人当前 TF / 定位把目标投影到地图
-> 行为树读取地图点
-> 选出一个安全的跟随点
-> 持续向 Nav2 下发更新后的路径
-> 目标移动时继续重规划
-> 目标失效时退出视觉接管
```

也就是说，视觉跟随真正接管的是“导航目标”，不是单独的 yaw / pitch。

## 3. 这次改动后的总体数据流

### 3.1 当前实际数据流

本次代码改完后，真实链路的数据流已经变成：

```text
sp_vision25 / Decider
  -> 继续产出 target_position_gimbal、yaw、pitch、tracking、confidence

sp_vision25 / io::Publish2Nav
  -> 读取 vision_fusion 配置
  -> 持有 tf2_ros::Buffer + TransformListener
  -> 将 target_position_gimbal 投影为 target_position_map
  -> 填充 has_target_position_map / target_position_map_frame
  -> 收紧 nav_hold
  -> 发布 /vision/target
  -> 额外发布 /vision/target_point_map

pb2025_sentry_behavior_server
  -> 继续订阅 /vision/target
  -> 继续维护 decision_current_pose
  -> 参数层新增 decision.pose.* 和 decision.vision.* 防抖参数

SelectVisionFollowPath
  -> 读取 vision_target
  -> 显式检查地图点是否有效
  -> 把目标点统一到规划 frame
  -> 把 current_pose 统一到规划 frame
  -> 基于 costmap 选跟随点
  -> 做最小重规划间隔和最小目标移动阈值防抖
  -> 输出 nav_msgs/Path

SendNavThroughPoses
  -> 向 Nav2 持续更新跟随路径
```

### 3.2 为什么把地图点投影放在 `Publish2Nav`

原方案里建议把地图点计算放进 `Decider` 或视觉融合主链。

这次实际实现时，我选择把投影逻辑放在：

- `src/sp_vision25/io/ros2/publish2nav.hpp`
- `src/sp_vision25/io/ros2/publish2nav.cpp`

原因是：

1. `Decider` 仍然专注“视觉目标是否存在、目标编号、相对云台位置、建议索引”等感知层语义。
2. 地图点投影本质上依赖 ROS2 TF，而不是视觉算法本身。
3. 把 TF 投影放在 ROS2 对外发布层，能尽量减少对 `omniperception` 主链的侵入。
4. 这样 `sentry`、`sentry_bp`、`sentry_debug`、`sentry_multithread` 只要统一走 `io::ROS2`，就都能自动获得相同的地图点语义。

换句话说，本次实现把“视觉算法输出相对点”和“ROS2 导航语义输出地图点”明确分成了两层。

## 4. 为什么不能直接用 `armor.xyz_in_world`

这是本次方案里最重要的理解点之一。

`auto_aim::Solver` 里虽然会计算：

```text
armor.xyz_in_world = R_gimbal2world * armor.xyz_in_gimbal
```

但这里的 `world` 更接近“云台绝对朝向下的旋转后向量”，并不包含导航地图中的平移项。

也就是说它只有：

```text
旋转
```

没有：

```text
机器人在地图中的平移位置
```

因此它不是：

```text
map 坐标系下的目标绝对点
```

而真实导航要消费的是：

```text
p_target_map = T_map_gimbal * p_target_gimbal
```

所以真正的地图点必须依赖 TF，而不能只依赖 `armor.xyz_in_world`。

## 5. 共享消息层做了什么

### 5.1 `VisionTargetMsg` 增量扩展

文件：

- `src/pb2025_sentry_nav/sp_msgs/msg/VisionTargetMsg.msg`

本次新增了两个字段：

```text
bool has_target_position_map
string target_position_map_frame
```

### 5.2 这样改解决了什么

它解决的是原来“靠 `(0,0,0)` 判断地图点无效”的隐式约定问题。

改完后，行为树不再需要猜：

1. 点值是不是全零。
2. 这个点到底属于 `map` 还是 `odom`。
3. 当前点值是“真目标”还是“占位值”。

现在语义变成：

1. `has_target_position_map == true` 才允许导航消费该点。
2. `target_position_map_frame` 明确说明该点属于哪个 frame。
3. 点值本身只表达数值，不再承担“是否有效”的附加含义。

## 6. `sp_vision25` 这边具体怎么落地

### 6.1 `VisionTargetState` 先扩容

文件：

- `src/sp_vision25/io/ros2/vision_target.hpp`

新增字段：

```cpp
bool has_target_position_map = false;
std::string target_position_map_frame;
```

这一步的意义是让 `sp_vision25` 内部状态先具备完整的导航语义，即便当前主链还没直接写这两个字段，ROS2 层也可以补齐。

### 6.2 `Decider` 仍然只负责“感知结果”

文件：

- `src/sp_vision25/tasks/omniperception/decider.cpp`

`Decider::build_vision_target_state()` 目前仍然保持较轻量：

1. `tracking = command.control`
2. `nav_hold = command.control`
3. 有目标时填 `target_position_gimbal`
4. 有目标时填 `target_distance`
5. 不再维护旧的固定导航点建议索引

注意：

本次没有把地图点投影写进这里。

这是刻意的。因为地图点投影依赖 ROS2 TF，放在发布层更合理。

### 6.3 `ROS2` 构造函数开始接收配置路径

文件：

- `src/sp_vision25/io/ros2/ros2.hpp`
- `src/sp_vision25/io/ros2/ros2.cpp`
- `src/sp_vision25/src/sentry.cpp`
- `src/sp_vision25/src/sentry_bp.cpp`
- `src/sp_vision25/src/sentry_debug.cpp`
- `src/sp_vision25/src/sentry_multithread.cpp`

原来：

```cpp
io::ROS2 ros2;
```

现在：

```cpp
io::ROS2 ros2(config_path);
```

这样 `Publish2Nav` 就能读取：

- `vision_fusion.map_frame`
- `vision_fusion.gimbal_frame`
- `vision_fusion.pose_timeout_s`
- `vision_fusion.nav_hold_min_confidence`
- `vision_fusion.publish_target_point_map`

### 6.4 `Publish2Nav` 变成真正的“视觉到导航接口层”

文件：

- `src/sp_vision25/io/ros2/publish2nav.hpp`
- `src/sp_vision25/io/ros2/publish2nav.cpp`

新增了几类核心能力。

#### 6.4.1 读取配置

通过 `loadVisionFusionConfig()` 读取：

```yaml
vision_fusion:
  map_frame: map
  gimbal_frame: gimbal_yaw
  pose_timeout_s: 0.2
  nav_hold_min_confidence: 0.6
  publish_target_point_map: true
```

对应文件：

- `src/sp_vision25/configs/sentry.yaml`

#### 6.4.2 持有 TF

`Publish2Nav` 内部新增：

```cpp
std::shared_ptr<tf2_ros::Buffer> tf_buffer_;
std::shared_ptr<tf2_ros::TransformListener> tf_listener_;
```

并在 `ensureTfListener()` 中惰性创建 listener。

这么做是为了：

1. 不让构造阶段过早依赖 `shared_from_this()`
2. 同时保证真正开始 `send_data()` 或 `start()` 时 TF 已经可用

#### 6.4.3 执行地图点投影

`tryProjectTargetPoint()` 的逻辑可以概括成：

```text
输入:
  target_position_gimbal
  gimbal_frame
  map_frame

步骤:
  1. 先检查 target_position_gimbal 是否 finite
  2. 构造 PointStamped(frame = gimbal_frame)
  3. lookupTransform(map_frame, gimbal_frame)
  4. 检查 TF 是否超时
  5. doTransform -> point_map
  6. 再检查 point_map 是否 finite

输出:
  成功 -> point_map + has_target_position_map = true
  失败 -> has_target_position_map = false
```

#### 6.4.4 支持两种地图点来源

`send_data()` 里现在不是强制只接受一种输入，而是按下面顺序工作：

1. 如果 `VisionTargetState` 里已经显式带了：
   - `has_target_position_map = true`
   - `target_position_map`
   - `target_position_map_frame`

   那就直接使用该地图点。

2. 否则回退到：
   - 用 `target_position_gimbal`
   - 通过 TF 做在线投影

这意味着后面如果你决定把地图点投影前移到更上游，当前接口层也仍然兼容。

#### 6.4.5 收紧 `nav_hold`

原来视觉侧接管导航的条件过松，基本等于：

```text
tracking = true
=> nav_hold = true
```

现在变成：

```text
allow_nav_hold =
  tracking
  && has_target_position_map
  && confidence >= nav_hold_min_confidence

message.nav_hold = data.nav_hold && allow_nav_hold
```

这一步很关键，因为它保证：

1. 云台能看见目标，不代表导航一定能接管。
2. 只有目标已经成功落到地图上，行为树才会切进视觉导航分支。
3. 目标丢失地图语义时，行为树会自然退出视觉接管。

#### 6.4.6 发布 RViz 调试点

新增话题：

```text
/vision/target_point_map
```

类型：

```text
geometry_msgs/PointStamped
```

这使得你在 RViz 中可以直接检查：

1. 视觉目标有没有成功落到导航地图上
2. 点的位置是不是和实际敌方位置一致
3. TF 是否稳定

### 7.2 一个重要的实现选择：没有把 TF 放进黑板

原始方案里建议：

```text
server 挂 tf2_ros::Buffer + TransformListener 到黑板
```

这次实际实现时，为了少改 server 主体，采用了更局部的方案：

1. `SelectVisionFollowPath` 自己持有 `tf_buffer_`
2. `IsPathGoalReached` 自己持有 `tf_buffer_`

优点是：

1. 改动范围更小
2. 不需要改 BT 黑板类型约定
3. 对现有插件结构侵入更少

缺点是：

1. TF 能力分散在多个节点里
2. 以后如果插件更多，可能再考虑统一到黑板

当前这个折中是合理的，已经足够支撑视觉跟随链路。

## 8. `SelectVisionFollowPath` 现在到底怎么工作

文件：

- `src/pb2025_sentry_behavior/include/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.hpp`
- `src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp`

这是本次行为树侧最核心的修改点。

### 8.1 新增的内部状态

类里新增了：

```cpp
std::shared_ptr<tf2_ros::Buffer> tf_buffer_;
std::shared_ptr<tf2_ros::TransformListener> tf_listener_;

geometry_msgs::msg::Point last_target_point_;
geometry_msgs::msg::Point last_selected_goal_;
nav_msgs::msg::Path last_path_;
std::optional<rclcpp::Time> last_plan_time_;
std::string last_plan_frame_id_;
bool has_cached_path_ = false;
```

这对应两类能力：

1. TF 变换能力
2. 重规划防抖缓存能力

### 8.2 当前位姿先做新鲜度判断

在真正规划前，会先检查：

```text
decision.pose.timeout_s
```

如果 `current_pose` 太旧，就直接失败，不让视觉路径继续接管。

这样做是为了避免：

1. 当前位姿停留在旧时间戳
2. 目标点是新的，机器人位姿却是旧的
3. 导致跟随圆心和机器人位置关系错误

### 8.3 规划 frame 的选择规则

`resolvePlanningFrame()` 的优先级是：

1. `current_costmap.header.frame_id`
2. `decision.pose.expected_frame`
3. `current_pose.header.frame_id`
4. `vision_target.target_position_map_frame`
5. 最后回退 `map`

这和原方案的思路一致：优先让规划直接贴着真正的 costmap frame 走。

### 8.4 视觉目标点不再用零点判断

`transformTargetPointToFrame()` 现在只看：

1. `vision_target.has_target_position_map`
2. `vision_target.target_position_map_frame` 是否为空
3. `target_position_map` 是否 finite

如果无效，直接返回失败。

这一步就是把原来：

```text
(0,0,0) == 无效
```

改成：

```text
has_target_position_map == false 才是无效
```

### 8.5 目标点和当前位姿统一到同一 frame

现在在规划前会明确做两次变换：

1. `transformTargetPointToFrame()`
2. `transformPoseToFrame()`

也就是说，不论：

1. 视觉点来自 `map`
2. 当前位姿来自 `odom`
3. costmap 在另一个 frame

最终都会被统一到一个规划 frame 中，再进入后续候选点计算。

这一步直接解决了原来最容易出问题的“frame 明明都对，数值却对不上”的问题。

### 8.6 跟随点生成逻辑没有变方向，但更稳了

核心思路仍然是：

```text
以目标点为圆心
以 attack_radius 为半径
优先选择机器人当前相对方向对应的圆周点
如果 costmap 上不可走，再绕圈找候选点
```

也就是：

1. 先算机器人相对于目标的偏好角 `preferred_angle`
2. 先取一圈上的首选点
3. 再按多个半径缩放和角偏移扫描候选点
4. 找到第一个可通行点就作为跟随点

这一步在几何上等价于：

```text
让机器人尽量保持“围绕目标的一定攻击半径”
```

### 8.7 costmap 也要和规划 frame 一致

现在新增了一个保护逻辑：

如果：

```text
costmap.frame != planning_frame
```

则不会强行拿这个 costmap 去筛候选点，而是打印 warning 并跳过 costmap 筛选。

这是为了避免更隐蔽的问题：

1. 目标点已经变到了 `map`
2. 但 costmap 却还是另一个 frame
3. 如果直接拿来算栅格索引，会得到完全错误的障碍判断

### 8.8 防抖逻辑是怎么做的

这是本次实机跟随稳定性的关键点。

函数：

```text
shouldReuseCachedPath()
cachePath()
resetCachedPath()
```

当前策略：

1. 如果没有缓存路径，第一次一定重规划。
2. 如果距离上次规划时间小于 `min_replan_interval_s`，直接复用旧路径。
3. 如果时间虽然到了，但新跟随点和旧跟随点的平面距离小于 `min_goal_shift_m`，仍然复用旧路径。
4. 只有“时间到了且目标变化足够明显”，才重新生成新路径。

这一步能明显减少：

1. 视觉测量噪声
2. TF 轻微抖动
3. 跟随圆采样点因为离散 costmap 造成的来回跳变

## 9. `IsPathGoalReached` 为什么也要改

文件：

- `src/pb2025_sentry_behavior/include/pb2025_sentry_behavior/plugins/condition/is_path_goal_reached.hpp`
- `src/pb2025_sentry_behavior/plugins/condition/is_path_goal_reached.cpp`

如果只改 `SelectVisionFollowPath`，而不改 `IsPathGoalReached`，还会留下一个问题：

```text
path 在 map
current_pose 在 odom
```

此时即便路径本身是对的，终点到当前位姿的距离判断也会错。

所以现在 `IsPathGoalReached` 也会在比较前：

1. 检查 `current_pose.header.frame_id`
2. 如果和 `path.header.frame_id` 不一致
3. 先用 TF 转到 path frame
4. 再做 goal reached 判断

这使得整个行为树分支在 frame 语义上更闭合。

## 10. loopback / fake vision 为什么也要同步改

文件：

- `src/pb2025_sentry_bringup/scripts/fake_decision_sim_inputs.py`
- `src/pb2025_sentry_bringup/launch/loopback_decision_sim.launch.py`
- `src/pb2025_sentry_bringup/launch/loopback_vision_test.launch.py`

本次新增了：

```text
vision_has_target_position_map
vision_target_position_map_frame
```

原因很简单：

如果仿真里还在用旧语义，而真机用新语义，那你在 loopback 里调通的东西到了实机就会失真。

现在 fake vision 也显式发布：

1. 地图点值
2. 地图点有效位
3. 地图点 frame

这样 loopback 和真机就共享同一套接口约定。

## 17. 教学版：沿着算法链路读源码

这一节我不再按“先讲完一个文件，再讲下一个文件”的方式展开，而是直接按一次视觉跟随闭环真实发生的顺序来讲。

也就是说，下面每一步都会同时回答 4 个问题：

1. 这一步的输入是什么。
2. 这一步的算法逻辑是什么。
3. 代码落在哪个文件、哪个函数里。
4. 这一步的输出会交给谁。

如果你只想先抓住全局，可以先记住下面这条主线：

```text
Decider
  -> 产出目标相对云台点 target_position_gimbal 和基础控制语义

Publish2Nav::send_data
  -> 展开 VisionTargetState
  -> 优先复用上游地图点，否则现场做 TF 投影
  -> 重新判定 nav_hold 是否真的允许导航接管

SelectVisionFollowPath::tick
  -> 检查输入是否齐全且新鲜
  -> 决定 planning frame
  -> 把目标点和当前位姿统一到同一 frame
  -> 围绕目标采样跟随点
  -> 用 costmap 筛点
  -> 用缓存和阈值做防抖
  -> 输出 Path 给 Nav2

IsPathGoalReached
  -> 把 current_pose 变到 path frame
  -> 判断是否已经到达本轮跟随终点
```

如果你只记两个公式，也够用了：

```text
p_target_map = T_map_gimbal * p_target_gimbal
goal_follow = target_point + r * [cos(theta), sin(theta)]
```

前一个公式解决“敌人到底在地图哪里”，后一个公式解决“我应该站到目标周围的哪个位置”。

### 17.1 第 0 步：先把 3 类“点”分清楚

文件：

- `src/pb2025_sentry_nav/sp_msgs/msg/VisionTargetMsg.msg`
- `src/sp_vision25/io/ros2/vision_target.hpp`

这一步不是在做计算，而是在先定义后面整条算法链到底在传什么。

最关键的是分清楚下面 3 个几何量：

```text
target_position_gimbal
  = 目标相对云台的三维点

target_position_map
  = 目标在地图坐标系下的绝对点

selected_point
  = 行为树最终选出来的跟随站位点
```

其中前两个会进入消息，第三个不会进入消息，而是 `SelectVisionFollowPath` 在本地计算。

对应的共享消息语义是：

```text
tracking / nav_hold / fire_permitted
  -> 控制层语义

target_position_gimbal
  -> 感知层最原始的几何输出

target_position_map + has_target_position_map + target_position_map_frame
  -> 导航层真正能不能消费这个目标点
```

这里最重要的，不是 `target_position_map` 这个数值本身，而是：

```text
这个点有没有效
这个点属于哪个 frame
```

所以这次文档和代码都在强化同一个观点：

```text
导航消费的不是“一个点”，而是“某个 frame 下的有效点”
```

### 17.2 第 1 步：`Decider` 先给出相对目标，不直接负责地图投影

文件：

- `src/sp_vision25/tasks/omniperception/decider.cpp`

输入：

```text
io::Command command
VisionTargetInfo target_info
```

算法逻辑：

1. 先把视觉控制语义写进状态里。
2. 如果当前没有有效目标，直接返回，不去伪造地图点。
3. 如果目标有效，就补齐相对云台点、目标距离、建议站位索引。

关键代码：

```cpp
io::VisionTargetState Decider::build_vision_target_state(
  const io::Command & command, const VisionTargetInfo & target_info) const
{
  io::VisionTargetState state;
  state.tracking = command.control;
  state.nav_hold = command.control;
  state.fire_permitted = command.shoot;
  state.target_id = target_info.target_id;
  state.confidence = target_info.confidence;
  state.target_yaw = command.yaw;
  state.target_pitch = command.pitch;

  if (!target_info.valid) {
    return state;
  }

  state.target_distance = target_info.position_gimbal.norm();
  state.target_position_gimbal = target_info.position_gimbal;
  return state;
}
```

这一段很值得学，因为它把职责边界切得很清楚：

```text
Decider 负责回答“看到了谁、相对我在哪里、该不该开火/跟踪”
Publish2Nav 才负责回答“这个目标能不能变成导航能吃的地图点”
```

为什么我认为这样更合理：

1. `Decider` 依赖的是视觉主链内部语义。
2. 地图投影依赖的是 ROS2 TF。
3. 把 TF 逻辑硬塞进感知决策层，会让模块边界变脏。

所以这一步的输出是：

```text
有语义的相对目标状态 VisionTargetState
```

但它还不是最终导航消息。

### 17.3 第 2 步：`ROS2 ros2(config_path)` 让发布层具备工程化语义

文件：

- `src/sp_vision25/io/ros2/ros2.hpp`
- `src/sp_vision25/io/ros2/ros2.cpp`
- `src/sp_vision25/src/sentry.cpp`
- `src/sp_vision25/src/sentry_bp.cpp`
- `src/sp_vision25/src/sentry_debug.cpp`
- `src/sp_vision25/src/sentry_multithread.cpp`

输入：

```text
config_path
```

算法逻辑：

这一步其实不是“算法计算”，而是在决定后面整个投影和接管逻辑要遵守哪些约束：

```text
vision_fusion.map_frame
vision_fusion.gimbal_frame
vision_fusion.pose_timeout_s
vision_fusion.nav_hold_min_confidence
vision_fusion.publish_target_point_map
```

也就是说，现在 `ROS2` 已经不只是一个转发壳子，它开始承担：

```text
把视觉输出翻译成导航可执行语义
```

这一步的重要性在于：

```text
算法逻辑真正落地时，坐标系、超时时间、置信度阈值都必须是可配置的
```

否则你只能在一台机器、一个 TF 树、一个实验环境里勉强跑通。

### 17.4 第 3 步：`Publish2Nav::send_data()` 先把状态展开，再决定地图点从哪里来

文件：

- `src/sp_vision25/io/ros2/publish2nav.cpp`

输入：

```text
VisionTargetState data
```

算法逻辑：

`send_data()` 并不是“简单发布消息”，它实际在做下面这件事：

```text
把视觉内部状态整理成一份导航能够直接消费的标准输出
```

主流程可以浓缩成下面这段伪代码：

```text
message = expand(data)

if upstream already has valid target_position_map:
  use it directly
else:
  tryProjectTargetPoint(target_position_gimbal)

if got target_position_map:
  fill target_position_map / has_target_position_map / frame
  optional publish /vision/target_point_map
else:
  mark map point invalid

recompute nav_hold using tracking + map point validity + confidence threshold
publish /vision/target
```

关键代码：

```cpp
sp_msgs::msg::VisionTargetMsg message;
message.timestamp = this->now();
message.tracking = data.tracking;
message.nav_hold = data.nav_hold;
message.fire_permitted = data.fire_permitted;
message.target_id = data.target_id;
message.confidence = static_cast<float>(data.confidence);
message.target_distance = static_cast<float>(data.target_distance);
message.target_yaw = static_cast<float>(data.target_yaw);
message.target_pitch = static_cast<float>(data.target_pitch);

message.target_position_gimbal.x = data.target_position_gimbal.x();
message.target_position_gimbal.y = data.target_position_gimbal.y();
message.target_position_gimbal.z = data.target_position_gimbal.z();
```

上面这一段只是“结构体展开”。

真正决定算法语义的，是下面这个分支：

```cpp
geometry_msgs::msg::PointStamped target_point_map;
bool has_target_point_map = false;
if (data.has_target_position_map && isFiniteVector(data.target_position_map) &&
  !data.target_position_map_frame.empty())
{
  target_point_map.header.stamp = message.timestamp;
  target_point_map.header.frame_id = data.target_position_map_frame;
  target_point_map.point.x = data.target_position_map.x();
  target_point_map.point.y = data.target_position_map.y();
  target_point_map.point.z = data.target_position_map.z();
  has_target_point_map = true;
} else {
  has_target_point_map = tryProjectTargetPoint(data.target_position_gimbal, target_point_map);
}
```

这一段的设计思想，我建议你直接记成一句话：

```text
优先复用上游结果；上游没给够，就在接口层补齐
```

这让整条链路具备两个好处：

1. 现在可以最小侵入跑通。
2. 以后如果地图点投影被前移到上游，接口层仍然兼容。

所以这一层本质上是：

```text
视觉输出 -> 导航语义输出
```

而不是普通的 topic 转发。

### 17.5 第 4 步：`tryProjectTargetPoint()` 负责把相对点真正投到地图

文件：

- `src/sp_vision25/io/ros2/publish2nav.cpp`

输入：

```text
target_position_gimbal
gimbal_frame_
map_frame_
```

算法逻辑：

这一步在数学上做的是：

```text
p_target_map = T_map_gimbal * p_target_gimbal
```

也就是把“目标相对云台的位置”变成“目标在地图里的绝对位置”。

关键代码：

```cpp
geometry_msgs::msg::PointStamped point_gimbal;
point_gimbal.header.stamp = this->now();
point_gimbal.header.frame_id = gimbal_frame_;
point_gimbal.point.x = target_position_gimbal.x();
point_gimbal.point.y = target_position_gimbal.y();
point_gimbal.point.z = target_position_gimbal.z();

const auto transform =
  tf_buffer_->lookupTransform(map_frame_, gimbal_frame_, tf2::TimePointZero);

tf2::doTransform(point_gimbal, point_map, transform);
point_map.header.frame_id = map_frame_;
point_map.header.stamp = this->now();
```

你可以把这一段理解成 3 个动作：

1. 先把三维向量写成“带 frame 的点”。
2. 向 TF 要一份 `gimbal_frame -> map_frame` 的变换。
3. 让 TF 帮你完成坐标变换。

这一步为什么不能直接依赖 `armor.xyz_in_world`，前面已经讲过原因，这里再压缩成一句：

```text
导航要的是带平移的地图绝对点，而不是只有旋转语义的世界向量
```

### 17.6 第 5 步：TF 不只是“有没有”，还必须“够不够新”

文件：

- `src/sp_vision25/io/ros2/publish2nav.cpp`

输入：

```text
transform.header.stamp
pose_timeout_s_
```

算法逻辑：

很多人第一次做 TF 投影，只会检查：

```text
lookupTransform 能不能成功
```

但这套实现往前多走了一步，它还检查：

```text
TF 虽然存在，但会不会已经旧到不能用于导航
```

关键代码：

```cpp
if (pose_timeout_s_ > 0.0 && (transform.header.stamp.sec != 0U ||
  transform.header.stamp.nanosec != 0U))
{
  const auto age_s = (this->now() - rclcpp::Time(transform.header.stamp)).seconds();
  if (age_s > pose_timeout_s_) {
    return false;
  }
}
```

为什么这里很重要：

1. 旧 TF 也会投出“看起来很正常”的地图点。
2. 这个点值未必会 NaN，也未必会报错。
3. 但它会把跟随点往机器人旧位置附近拖，导致路径抖动甚至跟丢。

所以这里的工程结论非常明确：

```text
TF stale = target_position_map 无效
```

这一步输出的不是“有没有变换成功”这么简单，而是：

```text
这份地图点能不能拿去参与导航闭环
```

### 17.7 第 6 步：`nav_hold` 不是跟踪标志，而是“可执行接管”的标志

文件：

- `src/sp_vision25/io/ros2/publish2nav.cpp`

输入：

```text
tracking
has_target_position_map
confidence
nav_hold_min_confidence_
```

算法逻辑：

这一步是整条链里语义最容易混的地方，所以我单独拿出来讲。

关键代码：

```cpp
const bool allow_nav_hold =
  message.tracking && message.has_target_position_map &&
  data.confidence >= nav_hold_min_confidence_;
message.nav_hold = data.nav_hold && allow_nav_hold;
```

它真正表达的不是：

```text
视觉现在有没有看到目标
```

而是：

```text
视觉现在给出的目标，够不够可靠到可以让导航接管
```

这里把 `tracking` 和 `nav_hold` 分开，是这次改动最关键的一个优化：

```text
tracking = 感知层状态
nav_hold = 行为树是否允许进入视觉接管分支
```

最终就把一个容易模糊的语义，变成了明确的算法判据：

```text
tracking && target_position_map valid && confidence ok
```

### 17.8 第 7 步：`SelectVisionFollowPath::tick()` 把地图目标变成实际跟随路径

文件：

- `src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp`

输入：

```text
VisionTargetMsg vision_target
PoseStamped current_pose
OccupancyGrid current_costmap
attack_radius / occupied_threshold / sample_count
min_replan_interval_s / min_goal_shift_m
```

算法逻辑：

这一整个函数其实就是“导航侧的核心算法”。

如果你把它压缩成一段伪代码，会非常清楚：

```text
if no vision_target or no current_pose:
  fail

if current_pose stale:
  fail and clear cache

planning_frame = resolvePlanningFrame(...)
target_point = transformTargetPointToFrame(...)
pose_in_planning_frame = transformPoseToFrame(...)

preferred_angle = angle from target to current robot
selected_point = point on follow circle at preferred_angle

if costmap frame matches planning_frame:
  search better traversable candidate around the ring

if cached path is still reusable:
  return cached path

path = buildFacingPose(selected_point, target_point)
cache path
return path
```

这一步真正解决的是：

```text
目标点已经知道了
那机器人应该站到目标周围哪里，并且什么时候需要重规划
```

也就是说，前面 `Publish2Nav` 解决的是“目标定位”，这里解决的是“站位规划”。

### 17.9 第 8 步：先检查输入有效性和时效性，再谈规划

文件：

- `src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp`

输入：

关键代码：

```cpp

  return BT::NodeStatus::FAILURE;
}

  resetCachedPath();
  return BT::NodeStatus::FAILURE;

```


这里的算法思想是：

```text

机器人自身位姿也要有效

```

很多系统会只盯着视觉目标新不新鲜，但实际上：

```text

```

而且这里调用 `resetCachedPath()` 也很关键，因为旧缓存如果继续保留，行为树可能会误以为还可以沿用上一轮路径。

这段代码背后的算法原则非常值得记：

```text

```

后面紧跟着的两个变换函数：

本质上是在保证：

```text

```

```cpp

```

```cpp
{
  return std::nullopt;
```

这意味着行为树不再依赖 `(0,0,0)` 这种隐式哨兵值，而是只认：

```text

```

这就是“显式协议优于隐式猜测”的直接落地。

### 17.11 第 10 步：围绕目标生成跟随圆，并优先保持当前相对方位

文件：

- `src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp`

输入：

```text
target_point
current_position
attack_radius
```

关键代码：

```cpp
const auto & current_position = transformed_current_pose->pose.position;
double preferred_angle = 0.0;
if (planarDistance(current_position, *target_point) > kPositionEpsilon) {
  preferred_angle = std::atan2(
    current_position.y - target_point->y, current_position.x - target_point->x);
}

geometry_msgs::msg::Point selected_point =
  sampleCirclePoint(*target_point, attack_radius, preferred_angle);
```

这一段对应的几何逻辑是：

1. 先看机器人当前位于目标的哪个方向。
2. 然后在目标周围半径为 `attack_radius` 的圆上，优先选择同方向的点。

为什么这种做法好：

```text
它会尽量保持机器人当前的包围方向，
而不是每一轮都把目标周围的站位重新洗牌
```

所以这里虽然代码很短，但它背后的站位策略非常明确：

```text
优先稳定，不优先炫技
```

这对实机跟随非常重要，因为你真正怕的不是“理论上不最优”，而是“站位点在目标周围乱跳”。

### 17.12 第 11 步：costmap 不是强行参与，而是满足 frame 条件后再参与筛点

文件：

- `src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp`

输入：

```text
current_costmap
planning_frame
occupied_threshold
sample_count
```

关键代码：

```cpp
const bool use_costmap_screening =
  costmap && !costmap->data.empty() && !costmap->header.frame_id.empty() &&
  costmap->header.frame_id == planning_frame;
```

```cpp
if (use_costmap_screening) {
  static constexpr std::array<double, 5> kRadiusScales{{1.0, 0.85, 0.7, 0.55, 0.4}};
  const auto angle_offsets = buildAngleOffsets(sample_count);

  bool found_candidate = false;
  for (const auto radius_scale : kRadiusScales) {
    const double radius = attack_radius * radius_scale;
    for (const auto angle_offset : angle_offsets) {
      const auto candidate =
        sampleCirclePoint(*target_point, radius, preferred_angle + angle_offset);
      if (!isTraversable(*costmap, candidate, occupied_threshold)) {
        continue;
      }
      selected_point = candidate;
      found_candidate = true;
      break;
    }
    if (found_candidate) {
      break;
    }
  }
}
```

这里的算法逻辑有两层。

第一层是：

```text
只有 costmap 和 planning_frame 一致时，才允许 costmap 参与筛点
```

这一步非常保守，但它是对的。因为如果 frame 都没对齐，costmap 再精细也会给出错误筛选结果。

第二层是：

```text
先从首选半径开始找；
找不到就逐步缩小半径；
每个半径上再围绕 preferred_angle 左右展开搜索
```

这相当于在做一个很轻量的局部候选搜索：

```text
尽量接近理想跟随圆
但允许为了可通行性做局部退让
```

这比“只试一个点”鲁棒得多，也比“全图找最优点”更轻。

### 17.13 第 12 步：缓存路径和重规划阈值负责给闭环降噪

文件：

- `src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp`

输入：

```text
now
planning_frame
selected_point
min_replan_interval_s
min_goal_shift_m
```

关键代码：

```cpp
if (shouldReuseCachedPath(
    now, planning_frame, selected_point, min_replan_interval_s, min_goal_shift_m))
{
  setOutput("path", last_path_);
  return BT::NodeStatus::SUCCESS;
}
```

```cpp
if ((now - *last_plan_time_).seconds() < min_replan_interval_s) {
  return true;
}

return planarDistance(selected_goal, last_selected_goal_) < min_goal_shift_m;
```

这一步是整条链的“防抖器”。

它采用的是双阈值策略：

```text
时间阈值：距离上次规划太近，不重规划
位移阈值：新目标和旧目标太接近，不重规划
```

为什么两个都要有：

1. 只有时间阈值，会错过真正发生的大位移变化。
2. 只有位移阈值，又容易在高频 tick 下频繁刷新同一条近似路径。

所以这里不是简单缓存，而是在做：

```text
视觉跟随闭环的节流 + 去抖
```

最后如果决定重新规划，就会生成一条只含一个站位 pose 的路径：

```cpp
nav_msgs::msg::Path path;
path.header.stamp = now;
path.header.frame_id = planning_frame;
path.poses.push_back(
  buildFacingPose(selected_point, *target_point, planning_frame, now));
cachePath(*target_point, selected_point, path, planning_frame, now);
```

这里 `buildFacingPose()` 的作用也很直观：

```text
位置站到 selected_point
朝向始终看向 target_point
```

所以最终输出给 Nav2 的不是“随便一个站位点”，而是：

```text
一个带朝向约束的跟随终点
```

### 17.14 第 13 步：`IsPathGoalReached` 也必须先统一 frame

文件：

- `src/pb2025_sentry_behavior/plugins/condition/is_path_goal_reached.cpp`

输入：

```text
path
current_pose
path_tolerance
```

关键代码：

```cpp

if (pose_in_path_frame.header.frame_id.empty()) {
  pose_in_path_frame.header.frame_id = path->header.frame_id;
} else if (!path->header.frame_id.empty() &&
  pose_in_path_frame.header.frame_id != path->header.frame_id)

    path->header.frame_id, pose_in_path_frame.header.frame_id, tf2::TimePointZero);
  geometry_msgs::msg::PoseStamped transformed_pose;
```

这一步看起来像个小收尾，但逻辑上它和前面的跟随点规划完全一致：

```text

```

否则会出现最难排查的一类 bug：

```text
路径是真的
当前位置也是真的
但“是否到达终点”的判断是假的
```

所以这一步的意义不是“补一个 TF 细节”，而是把“frame 一致性”贯彻到了闭环终点判定。

### 17.15 把整条链压缩成一版能背下来的伪代码

如果你想把这次视觉跟随改造真正吃透，我建议把下面这段伪代码背下来。

```text
vision side:
  target_info = choose_target(...)
  state = build_vision_target_state(command, target_info)

publish side:
  message = expand(state)
  if state already has valid map point:
    message.target_position_map = state.target_position_map
  else if TF(map <- gimbal) is available and fresh:
    message.target_position_map = project(state.target_position_gimbal)
  else:
    message.has_target_position_map = false

  message.nav_hold =
    state.nav_hold &&
    message.tracking &&
    message.has_target_position_map &&
    state.confidence >= nav_hold_min_confidence

behavior side:
  if no vision_target or no current_pose:
    fail
  if current_pose stale:
    fail

  planning_frame = resolvePlanningFrame(...)
  target_point = transformTargetPointToFrame(...)
  robot_pose = transformPoseToFrame(...)
  if target_point or robot_pose invalid:
    fail

  preferred_angle = atan2(robot - target)
  selected_goal = point_on_circle(target_point, attack_radius, preferred_angle)
  selected_goal = costmap_screen_if_possible(selected_goal)

  if cached path still reusable:
    reuse cached path
  else:
    path = pose(selected_goal, look_at=target_point)
    cache(path)

goal reached side:
  current_pose = transform_to_path_frame(current_pose)
  return distance(current_pose, path.goal) < tolerance
```

只要你能把这段伪代码和源码一一对上，这条链路就不再是“很多文件里散落的修改”，而会真正变成你脑子里一条清晰的算法流程。

### 17.16 从这次重构里最值得学的 6 个工程习惯

#### 1. 先分清语义层级，再写代码

```text
相对点、地图点、最终跟随点不是一个东西
```

如果一开始不把这 3 个量拆开，后面消息设计、TF 变换、行为树规划都会混。

#### 2. 感知层和导航层之间要有“语义翻译层”

`Publish2Nav` 的价值不只是 publish，而是把视觉主链输出变成导航真正能消费的协议。

#### 3. 显式有效位比隐式哨兵值可靠得多

```text
has_target_position_map 比 (0,0,0) 更值得信任
```

这能显著减少调试时的猜测成本。

#### 4. 所有几何计算前，先统一 frame

不是“出 bug 了再补一个 TF”，而是把 frame 统一作为第一原则。

#### 5. 接管逻辑必须绑定可执行条件

```text
tracking 不等于 nav_hold
```

看到目标不代表已经具备导航接管条件。

#### 6. 视觉闭环一定要带防抖

没有缓存、没有最小重规划间隔、没有最小目标位移阈值，Nav2 很容易被高频小抖动刷得不稳定。

这里不再重复讲设计原理，而是把“实机到底该怎么启动、先看哪条链、哪类日志说明卡在哪里”整理成一份现场可直接执行的清单。

### 18.1 先明确当前实机视觉跟随闭环

当前实机视觉跟随的闭环应当是：

1. `sp_vision25` 发布 `/vision/target`
2. 如果地图投影成功，`sp_vision25` 同时发布 `/vision/target_point_map`
3. `pb2025_sentry_behavior` 消费 `/vision/target`，在目标周围半圆上选跟随点，并发布 `/decision/vision_follow_markers`
4. `SendNavThroughPoses` 把选中的跟随点送给 `/navigate_through_poses`

所以实机调试时，建议始终按这个顺序排：

```text
TF -> /vision/target -> /vision/target_point_map -> /decision/vision_follow_markers -> /navigate_through_poses
```

### 18.2 实机测试前先检查 `sentry.yaml`

当前 `src/sp_vision25/configs/sentry.yaml` 里的 `vision_fusion` 配置为：

```yaml
vision_fusion:
  map_frame: map
  gimbal_frame: gimbal_yaw
  pose_timeout_s: 0.2
  nav_hold_min_confidence: 0.6
  publish_target_point_map: true
```

这 5 个字段名和当前代码实现是对齐的，没有拼写错误，也没有“参数虽然写了但代码根本不读”的问题。

结合当前代码，实机上应这样理解这 5 个参数：

1. `map_frame: map`

   这是视觉目标最终投影到导航全局坐标系时使用的目标 frame。

   当前行为侧默认也使用：

   ```text
   decision.pose.expected_frame = map
   ```

   所以如果你的定位、全局 costmap、行为树都运行在 `map`，这个值就是正确的。

2. `gimbal_frame: gimbal_yaw`

   这只有在实机 TF 树里真实存在 `map -> ... -> gimbal_yaw` 这条变换链时才是正确的。

   如果实机串口或机器人描述发布出来的 frame 名不是 `gimbal_yaw`，那么视觉地图点投影一定会失败，表现为：

   ```text
   /vision/target 里 tracking=true
   但 has_target_position_map=false
   ```

3. `pose_timeout_s: 0.2`

   这个值语义上没有问题，但它是这次实机最值得优先观察的风险点。

   它的含义是：

   ```text
   如果 map <- gimbal_yaw 这条 TF 太旧，超过 0.2s，
   就放弃本次 target_position_map 投影
   ```

   如果你现场定位更新时间不稳定、TF 有抖动、或者偶尔卡顿，那么 0.2s 可能偏紧。

   如果实机上出现“有时能跟、有时突然没有 target_position_map”的现象，第一优先怀疑这个值，建议试：

   ```yaml
   pose_timeout_s: 0.3
   ```

   或：

   ```yaml
   pose_timeout_s: 0.5
   ```

   改完后重启 `sp_vision25`。

4. `nav_hold_min_confidence: 0.6`

   当前代码里这个值暂时不会成为主要限制条件。

   因为现在 `Decider::get_target_info()` 里：

   ```text
   confidence = 1.0
   ```

   也就是说，只要目标有效，这个阈值通常都会通过。

   所以现场如果视觉跟随不起作用，不要优先怀疑这个参数。

5. `publish_target_point_map: true`

   这个值对实机调试非常重要，建议保持 `true`。

   它会让你在 RViz 和 `ros2 topic echo` 里直接看到：

   ```text
   /vision/target_point_map
   ```

   这样你能第一时间判断：

   1. 视觉是否真的把目标投到了地图里。
   2. 投影后的点是不是跳飞了。
   3. 当前问题是在视觉侧、TF 侧，还是行为树侧。

#### 18.3.3 如果这一轮改用 `sentry_debug` 做视觉跟随联调

如果你这轮的目标是：

1. 一边跑真实视觉跟随
2. 一边看识别、跟踪、重投影、网页调试面板
3. 同时继续让 `/vision/target` 和 `/vision/target_point_map` 送给行为树

那么终端 3 更推荐改成 `sentry_debug`，而不是普通的 `sentry`。

先注意 3 个关键事实：

1. `sentry_debug` 不是“只看图不发消息”的假调试程序。
   它在 `AutoAim` 模式下同样会：

   ```text
   gimbal.send(...)
   ros2.publish(vision_target_state)
   ```

   所以它可以直接参与视觉跟随闭环。

2. `sentry` 和 `sentry_debug` 不能同时启动。

   因为它们都会抢：

   ```text
   相机
   串口 / 云台
   vision/target 发布链
   ```

3. `sentry_debug` 默认会启动网页调试器。

   截至当前代码，网页调试器一旦启动，模式选择优先走网页侧选择，而不是串口回传档位。
   也就是说你做视觉跟随联调时，要确保网页里的模式保持在：

   ```text
   AutoAim
   ```

   不要切到 `SmallBuff` 或 `BigBuff`。

另外还有一个实机安全提醒：

当前 `src/sp_vision25/configs/sentry.yaml` 里仍然是：

```yaml
auto_fire: true
```

而 `sentry_debug` 在自瞄模式下会真实执行：

```text
fire = current_plan.fire
gimbal.send(...)
```

所以如果你这轮只想联调视觉跟随，不想让实机进入自动开火，请先改成：

```yaml
auto_fire: false
```

或者至少确保现场已经做了断弹 / 安全隔离。

### 18.4 现场第一轮健康检查

启动完成后，不要先盯“车为什么没动”，先按下面顺序确认链路有没有打通。

#### 1. 先确认节点和导航 action 都起来了

```bash
ros2 node list | grep -E 'sp_vision25|pb2025_sentry_behavior|bt_navigator'
ros2 action info /navigate_through_poses
```

正常现象：

1. 能看到 `sp_vision25`、`pb2025_sentry_behavior_server`、`bt_navigator`
2. `/navigate_through_poses` action 已经可用

如果这里就异常，不要继续怀疑视觉跟随算法，先把主链路补齐。

#### 2. 先看 TF 是否存在

```bash
source /opt/ros/humble/setup.bash
source /home/ats/ats_sentry_ws/install/setup.bash
ros2 run tf2_ros tf2_echo map gimbal_yaw
```

正常现象：

1. 能持续打印变换。
2. 变换数值随机器人位置和云台角度变化。

异常现象：

1. 报 `Invalid frame ID` 或 `lookup would require extrapolation`。
2. 长时间没有有效输出。

如果这里不正常，就先不要继续怀疑行为树，视觉目标地图点一定不稳定。

#### 3. 再看视觉消息本身

```bash
ros2 topic echo /vision/target --once
ros2 topic hz /vision/target
```

健康状态下，至少应重点看到这些字段：

```text
tracking: true
nav_hold: true
has_target_position_map: true
target_position_map_frame: map
```

如果 `tracking=true` 但 `has_target_position_map=false`，优先排查：

1. `gimbal_frame` 名称不对。
2. `map_frame` 名称不对。
3. `pose_timeout_s` 太小。
4. 实机定位或 TF 时间戳不新鲜。

#### 4. 再看地图点是否真的发布出来

```bash
ros2 topic echo /vision/target_point_map --once
ros2 topic hz /vision/target_point_map
```

如果这个话题完全没有消息，而 `/vision/target` 里又出现 `has_target_position_map=true`，说明你需要重点检查视觉节点是否真的在走当前这版安装产物。

#### 5. 再看行为树参数是否对齐

```bash
ros2 param get /pb2025_sentry_behavior_client target_tree
ros2 param get /pb2025_sentry_behavior_server decision.input_source
ros2 param get /pb2025_sentry_behavior_server decision.pose.expected_frame
ros2 param get /pb2025_sentry_behavior_server decision.vision.attack_radius
ros2 param get /pb2025_sentry_behavior_server decision.vision.follow_arc_half_angle_deg
ros2 param get /pb2025_sentry_behavior_server decision.vision.min_replan_interval_s
ros2 param get /pb2025_sentry_behavior_server decision.vision.min_goal_shift_m
```

当前默认期望值分别是：

```text
pb2025_sentry_behavior_client.target_tree = vision_test
decision.input_source = simulation
decision.pose.expected_frame = map
decision.vision.attack_radius = 2.0
decision.vision.follow_arc_half_angle_deg = 90.0
decision.vision.min_replan_interval_s = 0.4
decision.vision.min_goal_shift_m = 0.35
```

这里请特别注意前两项：

1. 如果你当前是按本文推荐的专项联调方式，`decision.input_source = simulation` 是正常现象。
2. 如果你后面切换成“保留 referee 回退”的自定义实机参数文件，那么这里就应该是：

   ```text
   decision.input_source = referee
   ```

如果你查出来还是：

```text
pb2025_sentry_behavior_client.target_tree = rmul_2026
```

那就说明你当前启动的不是视觉跟随调试树，后面即使 `/vision/target`、`/vision/target_point_map` 都正常，行为树也不会进入 `SelectVisionFollowPath`。

#### 6. 再看行为树是否真的选出了跟随点

先看 marker 话题：

```bash
ros2 topic echo /decision/vision_follow_markers --once
ros2 topic hz /decision/vision_follow_markers
```

只要行为树已经进入视觉跟随规划，这个话题就应该有消息。

然后同时观察终端 2 的日志，重点看有没有下面两类信息：

```text
Vision follow target=(...)
Send NavigateThroughPoses goal with ...
```

如果能看到第一类日志，说明行为树已经从视觉目标算出了新的跟随点。

如果还能看到第二类日志，说明这个跟随点已经真正送到了 Nav2 action。

如果日志里长期出现：

```text
Action server /navigate_through_poses is not available
```

那问题就已经不在视觉链，而在导航 action 链。

### 18.6 常见故障与优先排查顺序

#### 情况 0：压根没有 `/vision/target`

最优先排查：

1. `sp_vision25` 进程是否真的启动成功。
2. 相机、串口、模型文件、配置文件路径是否正常。
3. 终端 3 是否已经报出设备初始化失败。

#### 情况 1：`/vision/target` 有消息，但 `has_target_position_map=false`

最优先排查：

1. `ros2 run tf2_ros tf2_echo map gimbal_yaw` 是否正常。
2. `sentry.yaml` 里的 `gimbal_frame` 是否和实机 TF 名完全一致。
3. `pose_timeout_s` 是否过小。

#### 情况 2：`tracking=true`，但 `nav_hold=false`

最优先排查：

1. 视觉侧当前是不是故意没有放行导航接管。
2. `nav_hold_min_confidence` 是否设得过高。
3. 当前目标置信度、地图点有效位是否满足接管条件。

#### 情况 3：`/vision/target_point_map` 正常，但车不进入视觉跟随

最优先排查：

1. `/vision/target` 里的 `nav_hold` 是否为 `true`。
2. `/pb2025_sentry_behavior_client` 的 `target_tree` 是否真的是 `vision_test`。
3. `/pb2025_sentry_behavior_server` 的 `decision.input_source` 是否符合你当前调试预期。
4. `/pb2025_sentry_behavior_server` 的 `decision.pose.expected_frame` 是否是 `map`。
5. 终端 2 是否能看到 `Vision follow target=(...)` 这类日志。
6. `decision_current_pose` 对应的位姿输入是否还在持续更新。
7. 行为树是否真的加载的是 `sentry_behavior_vision_test.yaml`，或者你自定义的那份 `target_tree=vision_test` 参数文件。

#### 情况 4：marker 能看到，但车不动或 Nav2 不走

这说明：

```text
视觉点投影成功
行为树也已经选出了跟随点
问题更可能在 Nav2 执行链或底盘执行链
```

这时优先排查：

1. `/navigate_through_poses` action 是否可用。
2. 当前全局 costmap 是否把目标点附近判成不可通行。
3. 终端 2 是否出现 `Send NavigateThroughPoses goal with ...`。
4. 底盘控制链是否正常消费导航命令。

#### 情况 5：车能跟，但目标一抖就频繁重规划

优先调行为树参数：

```bash
ros2 param set /pb2025_sentry_behavior_server decision.vision.min_replan_interval_s 0.6
ros2 param set /pb2025_sentry_behavior_server decision.vision.min_goal_shift_m 0.45
```

如果你想让跟随更稳一些，而不是更灵敏一些，这两个参数应该先加大。

现场调参建议遵循一个原则：

```text

```

#### 视觉侧

如果地图点偶发丢失，建议优先改：

```yaml

  pose_timeout_s: 0.3
```

或：

```yaml

  pose_timeout_s: 0.5
```

改完后重启：

```bash

```

#### 行为树侧

如果你觉得围绕目标的跟随半径不合适，可以在线改：

```bash
ros2 param set /pb2025_sentry_behavior_server decision.vision.attack_radius 2.5
```

如果你发现跟随点经常选得过窄、过于保守，可以把半圆张角放宽：


```bash

ros2 param set /pb2025_sentry_behavior_server decision.vision.min_goal_shift_m 0.4
```
