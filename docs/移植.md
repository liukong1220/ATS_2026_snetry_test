# 哨兵导航与决策移植说明

## 1. 先说结论

当前项目已经完成了这一轮核心迁移：

1. 主决策树已经切到 `rmul_2026.xml`。
2. 局部控制主链已经切到 Nav2 MPPI。
3. 旧的“行为树直接围绕 `goal_pose` + 自研 PID 局部控制器”思路不再是主线。
4. loopback 和实机都走同一套行为树结构，只是输入源和参数文件不同。

所以“移植”这件事，在当前代码里不再是把旧 PID 控制器搬过来，而是把下面这条链路移植好：

```text
启动入口
  -> 行为树服务端
  -> 决策分支生成 decision_path
  -> SendNavThroughPoses
  -> Nav2 Planner + MPPI Controller
  -> 机器人执行
```

## 4. 当前与旧架构相比，到底迁移了什么

### 4.1 决策主树迁移

当前主树：

- [`../src/pb2025_sentry_behavior/behavior_trees/rmul_2026.xml`](../src/pb2025_sentry_behavior/behavior_trees/rmul_2026.xml)

历史树文件可能还在仓库里保留，但默认主线已经不是它们。

### 4.2 导航执行接口迁移

旧思路倾向于：

- 重复发布单个 `goal_pose`
- 再配套一个局部 PID / pursuit 控制链路

当前思路改成：

- 行为树生成 `nav_msgs/Path`
- `SendNavThroughPoses` 发送 `/navigate_through_poses`
- Nav2 自己完成路径规划与局部控制

这个变化的本质是：

1. 决策层不再直接操心“每一拍底盘该怎么跟踪”。
2. 决策层只负责“当前要走哪条路径、什么时候切路径”。
3. 局部跟踪由 MPPI 接管。

### 4.3 局部控制器迁移

当前主链的局部控制器是：

- `nav2_mppi_controller::MPPIController`

因此以前的 `pb_omni_pid_pursuit_controller` 已经不属于主线依赖。

如果你在当前代码树里搜索不到它，这是符合现状的，不是缺文件。

### 4.4 决策输入源迁移

当前行为树支持两种输入源：

1. `simulation`
2. `referee`

这让同一套主树既能跑：

1. loopback 轻量仿真
2. 实机裁判输入

而不需要维护两套完全独立的决策代码。

## 5. 当前参数文件之间的关系一定要分清

这是最容易改错的地方。

### 5.1 loopback 行为树参数

文件：

- [`../src/pb2025_sentry_behavior/params/sentry_behavior_loopback.yaml`](../src/pb2025_sentry_behavior/params/sentry_behavior_loopback.yaml)

作用：

1. 给 loopback 的行为树服务端使用
2. 默认 `decision.input_source = simulation`
3. 用来调巡逻点、退防点、安全点、视觉接管参数

### 5.2 实机行为树参数

文件：

- [`../src/pb2025_sentry_behavior/params/sentry_behavior.yaml`](../src/pb2025_sentry_behavior/params/sentry_behavior.yaml)

作用：

1. 给实机总入口下的行为树服务端使用
2. 默认 `decision.input_source = referee`
3. 用来调实车的行为树策略参数

### 5.3 loopback Nav2 参数

文件：

- [`../src/loopback_sim/params/nav2_params.yaml`](../src/loopback_sim/params/nav2_params.yaml)

作用：

1. 只服务于 loopback 仿真
2. 这里的 MPPI 参数只影响 `loopback_decision_sim.launch.py`
3. 用于快速复现“终点附近左右试探、转角反向抽动、轨迹乱飘”等问题

### 5.4 `pb2025_nav_bringup` 自带的实车 Nav2 参数

文件：

- [`../src/pb2025_sentry_nav/pb2025_nav_bringup/config/reality/nav2_params.yaml`](../src/pb2025_sentry_nav/pb2025_nav_bringup/config/reality/nav2_params.yaml)

作用：

1. 这是 `rm_navigation_reality_launch.py` 的默认 Nav2 参数文件
2. 当你单独启动 `pb2025_nav_bringup` 时，它会默认读这份
3. 它适合做“单独导航包”的基线配置

### 5.5 实机总入口真正默认使用的总参数文件

文件：

- [`../src/pb2025_sentry_bringup/params/node_params.yaml`](../src/pb2025_sentry_bringup/params/node_params.yaml)

这是当前最重要的一点：

> 当你用 `pb2025_sentry_bringup/launch/bringup.launch.py` 启动整套实机系统时，默认传给导航链路的不是 `pb2025_nav_bringup/config/reality/nav2_params.yaml`，而是这份 `node_params.yaml`。

原因是：

1. `bringup.launch.py` 的 `params_file` 默认值就是 `node_params.yaml`
2. 它把同一份 `params_file` 传给了串口侧和导航侧
3. 这份文件里不仅有硬件与定位参数，也包含了 Nav2 的 `bt_navigator`、`controller_server`、`planner_server` 等配置

因此：

- 你在实机总入口下调 MPPI，优先改 `node_params.yaml`
- 你在单独导航包下调 MPPI，优先改 `pb2025_nav_bringup/config/reality/nav2_params.yaml`

### 5.6 一句话记忆法

可以这样记：

1. 改 loopback 导航：改 `src/loopback_sim/params/nav2_params.yaml`
2. 改 loopback 决策：改 `src/pb2025_sentry_behavior/params/sentry_behavior_loopback.yaml`
3. 改实机决策：改 `src/pb2025_sentry_behavior/params/sentry_behavior.yaml`
4. 改实机总入口导航：改 `src/pb2025_sentry_bringup/params/node_params.yaml`
5. 改独立导航包默认导航：改 `src/pb2025_sentry_nav/pb2025_nav_bringup/config/reality/nav2_params.yaml`

## 7. 当前实机与仿真之间，哪些代码是共用的

共用部分：

1. 同一份主树 `rmul_2026.xml`
2. 同一套行为树插件
3. 同一套 `SendNavThroughPoses` 发送机制
4. 同一套巡逻/退防/安全点/视觉接管逻辑

不同部分：

1. 输入源不同  
   loopback 默认 `simulation`，实机默认 `referee`
2. Nav2 参数文件不同
3. 是否有真实串口、真实定位、真实裁判系统不同
4. 视觉消息发布端不同  
   loopback 用假数据，实机来自真实视觉系统

这也意味着：

> 你在 loopback 里发现的行为树逻辑错误，大概率在实机也会存在；你在 loopback 里调好的“纯决策层”问题，通常也能直接收益到实机。

但下面两类问题不能简单照搬：

1. 受实车动力学影响很大的 MPPI 参数
2. 依赖真实传感器时延、TF、costmap 质量的问题

## 9. 移植检查清单

### 9.1 把工程迁到新机器时

确认：

1. 地图和 pcd 资源是否放在 `pb2025_sentry_bringup/map` 与 `pcd`
2. `world` 参数是否能正确拼出地图路径
3. `node_params.yaml` 里的串口设备名、雷达参数、TF frame 是否符合新机器
4. 是否能单独拉起 `pb2025_nav_bringup`
5. 是否能单独拉起 `pb2025_sentry_behavior`

### 9.2 把旧项目逻辑迁到当前架构时

不要直接去找旧 PID 控制器入口，而应该：

1. 把旧的业务意图翻译成“选哪条 path”
2. 把目标点整理进 `decision.goal_points.*`
3. 把点位角色整理进 `decision.point_roles.*`
4. 在 `rmul_2026.xml` 里决定优先级
5. 让 Nav2 + MPPI 负责具体跟踪

### 9.3 把 loopback 调好的参数迁到实机时

建议只迁这两类：

1. 行为树点位和分支逻辑
2. 明显属于策略层的阈值参数

对于 MPPI 参数，建议：

1. 先迁一小部分
2. 再在实机慢速场景重新验证
3. 不要默认 loopback 最优值一定适合实车

## 10. 当前版本最重要的移植观念

如果后人只记住一句话，请记这句：

> 现在的“移植”不是把旧 PID 局部控制搬回来，而是要把启动入口、参数归属、行为树路径选择和 Nav2 MPPI 控制这四块边界分清楚。

分清边界后，后续维护就会非常顺：

1. 决策不对，去看行为树和点位角色。
2. 轨迹不对，去看 Nav2 / MPPI 参数。
3. 实机和仿真表现不一致，先看是不是改错了参数文件。
4. 视觉接管有问题，去看 `VisionTargetMsg` 链路和行为树视觉分支。
