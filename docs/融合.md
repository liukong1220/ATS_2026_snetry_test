# 视觉与导航融合说明

## 1. 文档目的

这份文档只描述当前仓库中已经落地的视觉融合链路，重点回答五个问题：

1. 视觉消息在当前项目里是怎么进入行为树的。
2. 行为树拿到视觉消息后，怎么决定是否接管导航。
3. 视觉接管后，导航目标点是怎么生成的。
4. loopback 和实机在视觉链路上共用哪些代码。
5. 后续维护时应该改哪些文件、先看哪些文件。

如果你当前更关注行为树整体结构，建议配合阅读：

- [`./sentry_bt_decision_checklist.md`](./sentry_bt_decision_checklist.md)

如果你当前更关注 MPPI 局部控制调参，建议配合阅读：

- [`./mppi_parameter_tuning_guide.md`](./mppi_parameter_tuning_guide.md)
- [`./mppi_local_plan_fix.md`](./mppi_local_plan_fix.md)

## 2. 先说当前代码里的真实边界

当前仓库中，视觉融合相关代码分成三块：

1. 消息契约层  
   [`../src/pb2025_sentry_nav/sp_msgs`](../src/pb2025_sentry_nav/sp_msgs)
2. 行为树消费层  
   [`../src/pb2025_sentry_behavior`](../src/pb2025_sentry_behavior)
3. loopback 假数据发布层  
   [`../src/pb2025_sentry_bringup/scripts/fake_decision_sim_inputs.py`](../src/pb2025_sentry_bringup/scripts/fake_decision_sim_inputs.py)

非常重要的一点是：

> 当前仓库里没有真实视觉算法本体；当前仓库负责的是“定义视觉消息格式、消费视觉消息、并在仿真时伪造视觉输入”。

也就是说，实机上的真实视觉发布端可以来自别的包，但只要它遵守同一条消息接口：

- `vision/target`
- `sp_msgs/msg/VisionTargetMsg`

当前行为树这边就能直接接上。

## 3. 为什么单独有一个 `sp_msgs`

消息定义所在位置：

- [`../src/pb2025_sentry_nav/sp_msgs`](../src/pb2025_sentry_nav/sp_msgs)

核心消息：

- [`../src/pb2025_sentry_nav/sp_msgs/msg/VisionTargetMsg.msg`](../src/pb2025_sentry_nav/sp_msgs/msg/VisionTargetMsg.msg)

把视觉消息单独放在 `sp_msgs` 里，有三个现实意义：

1. 视觉接口和裁判系统接口分层更清楚。
2. 视觉字段变化频率通常比底层串口协议更高，单独拆包更稳。
3. loopback、行为树、真实视觉发布端都可以依赖同一份消息定义，而不需要互相 include 对方的业务代码。

因此当前视觉融合不是“把视觉代码塞进导航包里”，而是“通过稳定消息契约解耦”。

## 4. `VisionTargetMsg` 每个字段在当前项目里是干什么的

文件：

- [`../src/pb2025_sentry_nav/sp_msgs/msg/VisionTargetMsg.msg`](../src/pb2025_sentry_nav/sp_msgs/msg/VisionTargetMsg.msg)

当前字段可以按用途分成四组。

### 4.1 有效性与新鲜度

- `timestamp`
- `tracking`
- `nav_hold`

含义：

1. `tracking` 表示视觉是否稳定追踪到目标。
2. `nav_hold` 表示视觉是否明确建议导航切入接管状态。
3. `timestamp` 让行为树知道这条结果是不是已经过期。

当前行为树不会因为“偶然看见了一帧目标”就接管，而是要求：

1. `tracking == true`
2. 如果配置要求，则 `nav_hold == true`
3. 时间戳没有超时

### 4.2 云台控制相关

- `target_yaw`
- `target_pitch`
- `target_id`

含义：

1. `target_yaw / target_pitch` 直接提供给云台绝对角指令。
2. `target_id` 当前主要用于观测和后续扩展。

### 4.3 调试与观测相关

- `confidence`
- `target_distance`

当前这两个字段更多服务于：

1. 日志观测
2. 调试时判断视觉结果是否稳定
3. 后续扩展决策权重

### 4.4 地图级跟随相关

- `target_position_gimbal`
- `target_position_map`
- `has_target_position_map`
- `target_position_map_frame`

其中真正驱动导航接管的核心是：

1. `target_position_map`
2. `has_target_position_map`
3. `target_position_map_frame`

因为当前视觉跟随路径生成已经不是“去固定编号点”，而是：

- 在敌方目标附近生成一个地图级可跟随位置

## 5. 当前视觉数据是怎么流到行为树里的

### 5.1 订阅入口

行为树服务端在这里订阅视觉话题：

- [`../src/pb2025_sentry_behavior/src/pb2025_sentry_behavior_server.cpp`](../src/pb2025_sentry_behavior/src/pb2025_sentry_behavior_server.cpp)

关键行为是：

1. 读取参数 `decision.vision.topic`
2. 默认订阅 `vision/target`
3. 把收到的 `VisionTargetMsg` 写进根黑板键：
   - `sp_vision_target`

所以从行为树视角看，视觉输入已经被统一抽象成：

- 一条黑板上的最新融合消息

### 5.2 行为树入口

顶层主树文件：

- [`../src/pb2025_sentry_behavior/behavior_trees/rmul_2026.xml`](../src/pb2025_sentry_behavior/behavior_trees/rmul_2026.xml)

视觉分支是：

- `vision_override_realtime`

它位于顶层 `ReactiveFallback` 的第一个分支，因此优先级最高。

### 5.3 当前完整执行链

```text
vision/target
  -> pb2025_sentry_behavior_server 订阅
  -> 写入黑板 sp_vision_target
  -> IsVisionTargetValid 判断能否接管
  -> PublishGimbalAbsolute 输出云台绝对角
  -> SelectVisionFollowPath 生成视觉跟随 path
  -> IsPathGoalReached / SendNavThroughPoses
  -> Nav2 + MPPI 执行
```

## 6. `IsVisionTargetValid` 到底筛掉了什么

文件：

- [`../src/pb2025_sentry_behavior/plugins/condition/is_vision_target_valid.cpp`](../src/pb2025_sentry_behavior/plugins/condition/is_vision_target_valid.cpp)

当前它的职责不是“判断敌人是不是存在于世界上”，而是“判断这条视觉消息是否足够可靠，可以让行为树切过去”。

它会做这些检查：

1. 黑板上是否有 `VisionTargetMsg`
2. `tracking` 是否为 `true`
3. 如果要求 `nav_hold`，则 `nav_hold` 是否为 `true`
4. `target_yaw / target_pitch` 是否是有限值
5. `timestamp` 是否有效
6. 消息年龄是否超过 `timeout_s`

只有全部通过后，它才会把这些值输出到黑板：

1. `vision_gimbal_yaw`
2. `vision_gimbal_pitch`
3. `vision_target_id`

这里的设计哲学是：

1. “看到目标”不等于“允许导航接管”
2. “上一帧还有目标”不等于“这一帧还能继续追”

这样才能避免：

1. 误检一帧就抢导航
2. 目标消失后继续追残留结果

## 7. `SelectVisionFollowPath` 的算法原理

文件：

- [`../src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp`](../src/pb2025_sentry_behavior/plugins/action/select_vision_follow_path.cpp)

这是当前视觉融合的核心算法节点。

### 7.1 它不是直接把目标点当导航终点

当前代码不会直接把：

- `target_position_map`

原封不动扔给 Nav2 当终点。

原因很简单：

1. 敌人位置本身可能不可达
2. 敌人位置上可能正好有障碍
3. 哨兵更合理的策略通常是“在敌人附近保持一个攻击半径”

所以当前策略是：

- 围绕敌方目标，在一个跟随圆环上选一个更适合导航和作战的点

### 7.2 选点流程

当前节点大致按下面步骤工作：

1. 读取 `VisionTargetMsg`
2. 读取当前机器人位姿 `current_pose`
3. 检查当前位姿是否过期
4. 解析规划坐标系 `planning_frame`
5. 把视觉目标点变换到规划坐标系
6. 以敌方目标为圆心、`attack_radius` 为半径，先得到一个“偏好跟随点”
7. 如果 costmap 可用，就在圆弧上采样多个候选点
8. 用 `follow_occupied_threshold` 过滤高占用点
9. 如果外层半径不合适，就尝试更小半径
10. 选中最终跟随点后，让机器人朝向敌方目标
11. 生成单点 `nav_msgs/Path`
12. 根据缓存与节流策略决定是否复用旧路径

### 7.3 为什么要做缓存和重规划节流

当前节点有两个非常重要的稳定器：

1. `min_replan_interval_s`
2. `min_goal_shift_m`

它们的意义是：

1. 目标点刚变化一点点时，不要每一帧都重发新路径
2. 在视觉抖动比较明显时，尽量让导航目标保持短时稳定

否则就很容易出现：

1. RViz 里可视化 marker 乱飘
2. 局部规划频繁左右换目标
3. MPPI 被高频重规划打乱

### 7.4 为什么生成的姿态是“朝向敌人”

当前路径里生成的 pose，不只是一个位置点，还会设置朝向：

- 让该 pose 的 yaw 面向 `target_position_map`

这样做的意义是：

1. 机器人接近目标后姿态更合理
2. 云台/底盘协同时更自然
3. 便于后续扩展基于朝向的开火或压制逻辑

### 7.5 为什么会发布 Marker

当前节点会往可视化话题发布 MarkerArray，用于观察：

1. 目标点在哪里
2. 跟随圆弧怎么展开
3. 最终选中了哪个跟随点

对应参数：

- `decision.vision.visualization_topic`

默认值在行为树参数里是：

- `decision/vision_follow_markers`

## 8. 视觉分支与普通巡逻/退防是什么关系

当前顶层结构里，视觉分支是实时 override，而不是并行建议。

这意味着：

1. 视觉合法时，优先走视觉跟随
2. 视觉不合法时，回退到 simulation 或 referee 分支
3. simulation/referee 分支本身不需要感知视觉细节

这种解耦有两个好处：

1. 普通导航逻辑保持稳定，不会和视觉细节强绑定
2. 视觉分支可以独立调试和迭代

从维护角度看，这相当于：

- 主树负责“是否交给视觉”
- 视觉子树负责“视觉接管后怎么跟随”

## 9. loopback 与实机的关系

### 9.1 loopback 怎么伪造视觉输入

文件：

- [`../src/pb2025_sentry_bringup/scripts/fake_decision_sim_inputs.py`](../src/pb2025_sentry_bringup/scripts/fake_decision_sim_inputs.py)

当前这个脚本会根据 launch 参数发布：

1. `decision/sim_mode`
2. 可选的裁判系统假消息
3. 可选的 `vision/target`

它发布的视觉消息字段语义和正式链路保持一致，因此它不是“随便发点假的东西”，而是：

- 在 loopback 里模拟真实视觉融合输出

### 9.2 loopback 和实机共用哪些部分

共用：

1. `VisionTargetMsg` 消息格式
2. `pb2025_sentry_behavior_server` 订阅逻辑
3. `rmul_2026.xml` 顶层优先级
4. `IsVisionTargetValid`
5. `SelectVisionFollowPath`
6. `SendNavThroughPoses`

不同：

1. loopback 的发布端是 `fake_decision_sim_inputs.py`
2. 实机的发布端来自真实视觉系统
3. loopback 的 Nav2/costmap/位姿质量与实机不完全一样

因此：

> 视觉分支的代码逻辑可以在 loopback 里先验证，但最终仍要在实机确认 TF、costmap、消息时延和目标抖动情况。

## 10. 视觉参数应该改哪里

### 10.1 loopback

文件：

- [`../src/pb2025_sentry_behavior/params/sentry_behavior_loopback.yaml`](../src/pb2025_sentry_behavior/params/sentry_behavior_loopback.yaml)

### 10.2 实机

文件：

- [`../src/pb2025_sentry_behavior/params/sentry_behavior.yaml`](../src/pb2025_sentry_behavior/params/sentry_behavior.yaml)

### 10.3 当前最关键的视觉参数

#### `decision.vision.timeout_s`

视觉消息最大允许年龄。

太小：

- 稍有时延就频繁掉出视觉分支

太大：

- 容易继续追已经过期的目标

#### `decision.vision.attack_radius`

围绕敌方目标生成跟随点的半径。

太小：

- 更容易贴近目标甚至贴到不可达区域

太大：

- 视觉接管会显得过于保守

#### `decision.vision.follow_occupied_threshold`

costmap 占用阈值。

太小：

- 候选点很容易被判死，不容易找到可用跟随点

太大：

- 容易选到离障碍太近的位置

#### `decision.vision.follow_sample_count`

圆弧采样数量。

太小：

- 候选点过稀，容易错过好点

太大：

- 计算量增加，但不一定显著增益

#### `decision.vision.follow_arc_half_angle_deg`

围绕偏好方向向左右扩展的采样半角。

太小：

- 候选范围太窄，障碍一挡就找不到点

太大：

- 候选范围太宽，可能绕到不想去的位置

#### `decision.vision.min_replan_interval_s`

最小重规划间隔。

太小：

- 视觉抖动会直接变成路径抖动

太大：

- 对目标变化反应会变慢

#### `decision.vision.min_goal_shift_m`

最小目标位移阈值。

太小：

- 目标稍微跳一下就重发 path

太大：

- 目标变化明显时也可能不及时更新

## 11. 常见问题从代码原理上怎么理解

### 11.1 为什么视觉明明在发，行为树却不接管

优先检查：

1. `tracking` 是否为 `true`
2. `nav_hold` 是否为 `true`
3. `timestamp` 是否新鲜
4. `target_yaw / target_pitch` 是否是有限值
5. `target_position_map` 是否真的有效

因为当前分支入口 `IsVisionTargetValid` 就会把这些情况直接挡掉。

### 11.2 为什么视觉接管了，但导航没有动

通常要看两层：

1. `SelectVisionFollowPath` 是否成功生成了 `decision_path`
2. `SendNavThroughPoses` 是否真的把路径发给了 Nav2

如果第一层失败，常见原因是：

1. 当前位姿过期
2. 目标点 frame 无法转换
3. 目标点不合法

### 11.3 为什么可视化 marker 看起来乱飘

先从原理上排查这几种情况：

1. 视觉目标本身就在抖
2. `min_replan_interval_s` 太小
3. `min_goal_shift_m` 太小
4. 目标点 frame 不稳定
5. 当前位姿本身在跳

也就是说，marker 乱飘不一定是可视化 bug，往往是“输入目标点或重规划频率本身就在乱”。

### 11.4 为什么机器人会围着敌方目标左右犹豫

这往往不是单一节点问题，而是三层叠加：

1. 视觉分支频繁改目标
2. `SelectVisionFollowPath` 的跟随点在左右来回切
3. MPPI 在局部控制上又对这些变化过度敏感

所以这类问题通常需要同时看：

1. 视觉参数
2. 行为树重规划节流参数
3. MPPI 参数

## 13. 当前版本最重要的结论

如果只记住一句话，请记这句：

> 当前视觉融合的本质不是“视觉告诉导航去哪个固定点”，而是“视觉给出一个地图级目标位置，行为树判断是否接管，再由 `SelectVisionFollowPath` 在敌方周围生成更合理的跟随点交给 Nav2/MPPI 执行”。

理解了这一点，后续你就知道：

1. 视觉问题不只看视觉话题，还要看行为树入口条件。
2. 导航问题不只看 MPPI，还要看视觉目标是否稳定。
3. loopback 和实机虽然发布端不同，但接管逻辑本身是同一套代码。
