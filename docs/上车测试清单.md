# 上车测试清单

> 适用于当前已经完成实车链路稳定导航后的继续上车测试。
>
> 当前重点不再是“能不能规划、能不能动”，而是确认轨迹质量、ESDF 作用、速度链和实车响应是否一致。

---

## 1. 本轮测试目标

本轮上车优先确认下面五件事：

1. 实车导航是否继续稳定，不再出现明显走走停停。
2. `smoothed_path_visual` 是否就是 controller 实际跟踪的那条平滑路径。
3. `/trajectory_profile`、`trajectory_profile_markers` 和实际速度变化是否一致。
4. signed Traversability ESDF 的红绿点、黄色梯度箭头是否和 traversability / costmap / 障碍位置一致。
5. 若速度变慢，能否定位是 profile 曲率、governor、velocity smoother 还是底盘响应导致。

### 2.3.1 这些 RViz 可视化分别是什么意思

建议先记住一句最实用的话：

- `plan` 看 planner 想怎么走
- `smoothed_path_visual` 看 smoother / optimizer 实际把线改成什么样
- `trajectory_profile_markers` 看这条线上的速度和曲率压力大不大
- `trajectory_esdf_debug` 看 signed ESDF 觉得哪里离障碍近、应该往哪边推开
- `traversability_*_grid` 看 ESDF 风险是否来自高度差、占据率或地面置信度

具体解释：

1. `plan`
   - 这是 SmacPlannerHybrid 的原始全局路径。
   - 主要用来判断原始规划是否已经贴墙、切角、终端被拉直。

2. `smoothed_path_visual`
   - 这是 B 样条平滑和 obstacle refinement 之后的可视化路径。
   - 如果它比 `plan` 更早从墙边回拉，说明平滑/避障在起作用。
   - 如果它反而内切进障碍边缘，说明 refinement 太激进或 corridor 太松。

3. `trajectory_profile_visual`
   - 这是轨迹 profile 的路径表达，主要对应带时间参数化后的轨迹。
   - 一般配合 `trajectory_profile_markers` 一起看。

4. `trajectory_profile_markers`
   - 青色折线和点表示 profile 路径。
   - 点的颜色大致表示该点速度相对速度上限的比例。
   - 尾部文字 `kappa_max=... cost=...` 是这一条轨迹的摘要。
   - 如果这条线和 `smoothed_path_visual` 明显不一致，说明 profile 发布或 smoother 输出链路需要检查。

5. `trajectory_esdf_debug`
   - 红绿点表示路径采样点到障碍物的距离状态。
   - 越偏红，表示越靠近障碍或已进入 signed ESDF 负值风险区；越偏绿，表示越安全。
   - 黄色小箭头表示 `grad d(x)`，也就是“当前这个点往哪边移动会更远离障碍”。
   - 尾部文字 `d_min / d_avg / |g|avg / risk_count` 是整条轨迹的 ESDF 摘要。

6. `traversability_grid`
   - 看 `terrain_analysis_ext` 对二维地形可通行性的最终判断。
   - 如果大片未知或大片障碍，优先查点云、地面估计和 terrain 参数。

7. `traversability_height_diff_grid`
   - 看高度差风险来源。
   - 如果 ESDF 红点和高度差热点一致，说明是地形突变导致的风险。

8. `traversability_occupancy_ratio_grid`
   - 看垂向占据率风险来源。
   - 如果墙边、障碍边缘占据率高，ESDF 应该同步变危险。

9. `traversability_ground_confidence_grid`
   - 看地面置信度。
   - 低置信区域如果触发 ESDF 风险，需要结合实际点云判断是合理保守还是误杀。

10. `local_costmap/costmap` 和 `global_costmap/costmap`
   - 这是 Nav2 看到的障碍和膨胀层。
   - 用它确认 ESDF 红点是不是真的对应墙角、膨胀层、还是传感器噪声。

11. `Obstacle Scan`
   - 看实时障碍输入是否正常。
   - 如果 costmap 很怪，先怀疑 scan / 点云链路，不要先怪 optimizer。

12. `TF`
   - 看 `map / odom / base_footprint / gimbal_yaw_odom / gimbal_yaw / gimbal_yaw_fake` 是否稳定。
   - 如果 TF 抖，轨迹看起来“像是优化有问题”，其实可能是状态估计或坐标链问题。

### 2.3.2 这些文字分别代表什么

#### A. `trajectory_esdf_debug` 里的文字

当前会显示：

- `d_min`
- `d_avg`
- `|g|avg`
- `risk_count`

它们的意思是：

1. `d_min`
   - 全轨迹采样点里，离最近障碍物的最小距离，单位是米。
   - 这是最危险的那个点。
   - 越小越危险；如果明显小于 `obstacle_safe_distance`，说明这条线某一段已经很贴边。

2. `d_avg`
   - 全轨迹采样点的平均障碍距离，单位是米。
   - 它不是“安全下限”，更像“整条路径整体离障碍远不远”。
   - `d_min` 小但 `d_avg` 大，通常表示只有局部一小段危险。

3. `|g|avg`
   - 全轨迹采样点的平均梯度模长，`g` 指 `grad d(x)`。
   - 可以粗略理解成“距离场在这条路径附近变化得强不强”。
   - 值偏大通常说明路径附近有更明显的障碍边界可供推离。
   - 值偏小不一定是好事，也可能是处在平坦区域、对称峡谷中线，或者局部梯度不明显。

4. `risk_count`
   - 当前写法是 `risk=a/b`。
   - `b` 是参与统计的总采样点数量。
   - `a` 是其中距离小于 `obstacle_safe_distance` 的危险点数量。
   - 它回答的问题是：这条路径里“危险采样点多不多”，不是只看最危险的一个点。

#### B. `trajectory_profile_markers` 里的文字

当前会显示：

- `kappa_max`
- `cost`

它们的意思是：

1. `kappa_max`
   - 这条轨迹上的最大绝对曲率。
   - 可以粗略理解为“最急的弯有多急”。
   - 越大通常表示某一段弯得越猛，对控制器越难跟。

2. `cost`
   - 这是当前轨迹 profile 的总 cost。
   - 代码里它等于：
     - `curvature_penalty`
     - `velocity_smoothness_cost`
     - `obstacle_cost`
     三项相加。
   - 所以它不是单独表示“碰撞代价”，而是整个轨迹当前综合代价。
   - `cost` 变大，可能是弯太急，也可能是速度剖面不平滑，也可能是更贴障，不要只按一个方向解释。

### 2.3.3 两组文字为什么会重叠

原因很简单：

1. `trajectory_profile_markers` 的 `kappa_max / cost` 文字默认挂在轨迹尾部上方。
2. `trajectory_esdf_debug` 的 `d_min / d_avg / |g|avg / risk_count` 之前也挂在差不多的位置。
3. 两者都属于“尾部摘要文字”，RViz 就容易叠在一起。

当前已经做的修正：

1. `kappa_max / cost` 仍然挂在轨迹尾部正上方。
2. `d_min / d_avg / |g|avg / risk_count` 改成沿轨迹末段的局部法向偏移后再抬高显示。
3. 这样正常情况下两组文字会稳定错开，不再挤在同一块区域。

### 2.3.4 速度链每一级代表什么

实车速度慢时不要只看最终 `/cmd_vel`，建议按下面顺序看：

1. `/trajectory_profile`
   - 这是 smoother 生成的轨迹剖面，里面有路径长度、时间、曲率、速度上限、速度、加速度和 cost。
   - `max_abs_curvature` 很大时，说明轨迹本身有急弯，后面速度变小是合理结果。
   - 如果 `curvature_penalty` 明显大于 `obstacle_cost`，问题更偏向曲率，不是贴障。

2. `/cmd_vel_controller`
   - 这是 MPPI controller 的原始输出。
   - 如果这里已经只有 `0.0x`，说明 controller 自己因为路径、costmap、critic 或目标关系给出了很小速度。

3. `/cmd_vel_controller_governed`
   - 这是 `trajectory_speed_governor` 根据近端 trajectory profile 做二次限速后的输出。
   - 它会看 `curvature_window_points` 内的近端曲率，而不是拿整条路径最急弯压低当前速度。

4. `/cmd_vel_nav2_result`
   - 这是 velocity smoother 输出给速度坐标变换节点的 Nav2 结果。
   - 如果这里比 governed 小很多，再看 velocity smoother 的速度、加速度、timeout 和 deadband 参数。

5. `/cmd_vel`
   - 这是 `fake_vel_transform` 坐标变换并叠加自旋后的最终底盘速度。
   - 下位机最终读的是这个话题对应的串口速度字段。

## 3. 分轮测试顺序

建议按下面顺序逐轮进行。

不要一开始就混合所有场景，否则很难判断是哪一层逻辑起作用。

### 第一轮：空旷区域普通导航

目标：

1. 建立实车速度和轨迹质量的基线。
2. 确认不会在空旷区域仍然低速 `0.0x`。
3. 确认 `smoothed_path_visual`、`trajectory_profile_markers`、`/cmd_vel` 三者趋势一致。

场景建议：

1. 选择空旷区域。
2. 起点和目标之间不要刻意贴墙。
3. 给 2 到 5 米的普通导航目标。

重点看：

1. `/trajectory_profile.max_abs_curvature` 是否处在合理范围。
2. `/cmd_vel_controller` 是否已经有正常线速度。
3. `/cmd_vel_controller_governed` 是否只是轻微收缩，而不是压到 `0.0x`。
4. 机器人实际运动是否连续。

### 第二轮：贴近膨胀层边缘导航

目标：

1. 验证 signed Traversability ESDF 是否能把贴边路径往安全侧回拉。
2. 验证 footprint / inflation_radius 是否没有把 free-space 路径判得过严。

场景建议：

1. 让全局路径经过墙边或障碍物边缘。
2. 不要一开始就贴死障碍，先做轻度贴边。
3. 再逐步提高难度。

重点看：

1. `plan` 是否本来就贴墙。
2. `smoothed_path_visual` 是否比 `plan` 更远离红色 ESDF 点。
3. `d_min / risk` 是否和肉眼看到的贴障程度一致。
4. `traversability_*_grid` 是否能解释红点来源。
5. 如果 fallback 到 raw path，raw path 是否真的更安全。

### 第三轮：恢复动作与动态遮挡

目标：

1. 验证动态障碍简单速度预测是否生效
2. 验证是否能比以前更早重规划

场景建议：

1. 先让机器人进入恢复动作
2. 然后让人或另一台机器人短时从恢复走廊前方经过
3. 不要直接完全贴死，优先做“逐渐逼近恢复走廊”的遮挡

重点看：

1. 是否比以前更早重规划
2. 是否少了“碰到边界才急停”的现象
3. 是否出现过早保守，明明还能走却不走

### 第四轮：普通导航阶段动态干扰

目标：

1. 判断当前动态障碍预测是否只够恢复层使用
2. 判断下一步是否该扩展到局部参考轨迹层

场景建议：

1. 不刻意制造恢复
2. 只让机器人做普通导航
3. 在其局部前进方向附近让动态障碍经过

重点看：

1. 普通导航是否也会被动态障碍反复打断
2. 打断主要发生在恢复阶段，还是正常 `FollowPath` 阶段
3. 若普通导航阶段也频繁犹豫，说明下一步应扩展到局部参考轨迹层

## 4. 现场该怎么看

### 4.1 普通导航是否连续

看：

1. 机器人实际动作
2. `/cmd_vel`
3. `/cmd_vel_controller`
4. `/trajectory_profile`

理想现象：

1. 机器人加速、巡航、减速过程连续。
2. `/cmd_vel_controller` 和 `/cmd_vel` 不再长期停在 `0.0x`。
3. `/trajectory_profile` 的前几个点速度和 RViz 中的轨迹形状能对上。

异常现象：

1. 机器人仍然明显一顿一顿
2. `/cmd_vel_controller` 已经很小，说明 MPPI 原始输出就偏保守
3. `/cmd_vel_controller` 正常但 `/cmd_vel` 很小，说明问题更可能在 governor、velocity smoother 或速度变换链

### 4.2 贴边路径是否被 ESDF 正确回拉

看：

1. `plan`
2. `smoothed_path_visual`
3. `trajectory_esdf_debug`
4. `traversability_grid`
5. `traversability_height_diff_grid`
6. `traversability_occupancy_ratio_grid`
7. `traversability_ground_confidence_grid`
8. `global_costmap/costmap`

理想现象：

1. `plan` 如果贴墙，`smoothed_path_visual` 应该有轻微回拉。
2. ESDF 红点应该集中在真实贴障段或地形语义风险高的区域。
3. 黄色梯度箭头应大体指向远离障碍的一侧。
4. `d_min / risk` 和肉眼看到的危险段一致。

异常现象：

1. ESDF 红点出现在明显空旷区域，优先怀疑 traversability 语义栅格、costmap、scan 或 TF。
2. 黄箭头方向和障碍关系相反，优先怀疑 map frame 或 costmap 数据。
3. `smoothed_path_visual` 比 `plan` 更贴障，优先怀疑 refinement 过强或走廊约束过松。

### 4.3 速度变慢时怎么定位

看：

1. `/trajectory_profile`
2. `/cmd_vel_controller`
3. `/cmd_vel_controller_governed`
4. `/cmd_vel_nav2_result`
5. `/cmd_vel`

理想现象：

1. 空旷路径中 `max_abs_curvature` 不应异常大。
2. `curvature_penalty` 不应长期压倒其他 cost。
3. governed 速度只做合理收缩，不应把正常 controller 输出压到接近 0。
4. `/cmd_vel_nav2_result` 和 `/cmd_vel` 应保持连续。

异常现象：

1. `max_abs_curvature` 很大，先回看 planner / smoother 路径形状。
2. `/cmd_vel_controller` 已经很小，先看 MPPI critic、局部 costmap、目标距离和 TF。
3. `/cmd_vel_controller_governed` 明显小很多，先看 governor 曲率窗口和制动增益。
4. `/cmd_vel_nav2_result` 明显小很多，先看 velocity smoother 限制。
5. `/cmd_vel` 断续，先看 `fake_vel_transform` 输入、odom/local_plan 同步和下位机订阅链。

### 4.4 动态障碍是否引起反复打断

重点观察：

1. 普通导航是否开始明显犹豫。
2. 动态障碍只是擦边经过时，是否过早放弃当前路径。
3. 恢复动作是否仍然过早保守。
4. recovery marker 是否每拍大幅跳变。

如果出现：

1. 过早保守
   - 优先怀疑 `prediction_horizon_s`
   - `predictive_block_margin`
   - `monitor_lookahead_distance`
2. 方向不自然
   - 优先怀疑恢复几何仍太“直线化”
   - 下一步考虑圆弧 / 样条恢复轨迹
3. 普通导航也被反复打断
   - 说明动态障碍预测应该扩展到局部参考轨迹层

### 4.5 上车时怎么把这些可视化串起来理解

建议按这个顺序看，不容易乱：

1. 先看 `plan`
   - 判断原始 planner 有没有先天贴墙、切角、终端拉直。

2. 再看 `smoothed_path_visual`
   - 判断 optimizer/smoother 是在把坏路径修好，还是反而修坏。

3. 再看 `trajectory_esdf_debug`
   - 看红点是不是正好落在贴墙段。
   - 看黄箭头方向是不是符合直觉。
   - 看 `d_min / risk_count` 是不是和你肉眼看到的危险段一致。

4. 再看 `trajectory_profile_markers`
   - 如果 `kappa_max` 很大，说明轨迹某段很急。
   - 如果 `cost` 很大，但 `d_min` 其实不小，那问题更可能在曲率或速度剖面，不一定是贴障。

5. 最后再对照机器人实际运动
   - 路径看着对但车走得抖，优先怀疑 odom / TF / 下位机响应。
   - 路径本身就贴墙或拧巴，再回头看 planner/smoother/ESDF。

## 7. 测试结论怎么决定下一步

### 情况 A：普通导航稳定，但贴边段仍内切

下一步做：

- 优先看 ESDF 梯度和 footprint / inflation_radius 是否匹配。
- 再考虑微调 obstacle refinement，不要直接提高 obstacle weight。

### 情况 B：路径正确，但速度仍明显偏慢

下一步做：

- 先看 `/trajectory_profile.max_abs_curvature` 和前几个 profile 点速度。
- 再看 `/cmd_vel_controller` 是否已经变小。
- 最后才考虑 MPPI critic 或 velocity smoother。

### 情况 C：普通导航阶段也会被动态障碍反复打断

下一步做：

- 把动态障碍预测从恢复层扩展到局部参考轨迹层

## 8. 当前这一轮的最重要结论标准

如果你这次上车回来，能明确回答下面五个问题，就已经足够支撑下一阶段决策：

1. 空旷区域普通导航速度是否正常。
2. 贴边路径中 `smoothed_path_visual` 是否比 `plan` 更合理。
3. ESDF 的 `d_min / risk` 是否和真实障碍关系一致。
4. 速度变慢时，是 profile 曲率、MPPI 输出、governor、velocity smoother 还是底盘响应导致。
5. 是否出现新的副作用，比如过早保守、fallback 过多或动态障碍引起反复打断。

只要这五项记录清楚，下一轮优化就能非常有针对性。
