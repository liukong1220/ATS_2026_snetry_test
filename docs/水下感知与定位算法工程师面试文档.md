## 1. 面试主线

### 1.1 一分钟自我介绍

我主要做 ROS2 机器人导航、定位和感知工程化，项目是 RoboMaster 哨兵机器人自主导航系统。这个项目里我参与了从传感器接入、LiDAR-IMU 里程计、点云重定位、地形感知、Nav2 规划控制、行为树决策到 Gazebo/loopback 仿真的完整链路。

系统使用 Livox Mid-360、IMU、工业相机和底盘里程信息，定位链路上用 Point-LIO 做 LiDAR-IMU 局部里程计，用 small_gicp 做 scan-to-map 全局重定位，并通过 `map -> odom -> lidar_odom/chassis` 的 TF 链给导航模块提供连续位姿。导航上使用 SmacPlannerHybrid、B-spline smoother、MPPI controller，并扩展了 traversability grid 到 ESDF 的轨迹安全约束。

虽然我的项目平台是陆上高速移动机器人，不是水下 ROV/AUV，但它和水下感知定位岗位在底层能力上高度相通：都需要处理多源传感器时序、外参、坐标系、状态估计、弱观测环境下的鲁棒定位、感知结果到导航控制的闭环，以及 C++/Python/ROS2 的工程落地。我希望把这套实机调试和算法工程化经验迁移到水下视觉、DVL/USBL/IMU 融合定位和水下目标检测跟踪任务中。

### 1.2 三分钟项目介绍

ATS 2026 哨兵机器人项目是一个完整的 ROS2 自主移动机器人系统，主要分为五层：

1. 启动编排层：`pb2025_sentry_bringup`，负责实机、仿真、参数和 RViz 启动。
2. 决策层：`pb2025_sentry_behavior`，使用 BehaviorTree.CPP 管理巡逻、视觉接管、受击闪避、资源状态切换。
3. 导航与定位层：`pb2025_sentry_nav`，包含 Point-LIO、small_gicp、terrain analysis、Nav2、MPPI、B-spline smoother 和自定义恢复行为。
4. 仿真层：`loopback_sim` 和 `rmu_gazebo_simulator`，分别用于轻量闭环测试和 Gazebo 传感器/环境仿真。
5. 设备接口层：`standard_robot_pp_ros2`，负责串口桥、裁判系统和底盘命令。

定位链路是：Mid-360 点云和 IMU 进入 Point-LIO，得到连续局部里程计；small_gicp 将当前注册点云与先验 PCD 地图匹配，输出 `map -> odom` 修正；下游 Nav2 基于稳定 TF 做全局规划和局部控制。感知链路是：点云经过 terrain analysis 生成障碍点云和 traversability grid，再由 ESDF provider 转成可用于 B-spline 平滑器的障碍距离场。控制链路是：SmacPlannerHybrid 生成全局路径，B-spline smoother 进行平滑和离障约束，MPPI 做局部控制，最后通过速度平滑和云台坐标补偿输出 `/cmd_vel`。

这个项目最像水下岗位的地方有三点：

1. 多传感器融合：我处理过 LiDAR/IMU/相机/底盘数据的坐标系、时间戳、频率差异和模块解耦；迁移到水下就是 Camera/IMU/DVL/USBL/深度计/RTK 的融合问题。
2. 弱结构环境定位：比赛场地存在高速运动、遮挡、退化结构和重定位失败风险；水下环境则是弱纹理、浑浊、光照变化和声学观测稀疏，本质上都要求鲁棒状态估计和异常处理。
3. 工程闭环：我不是只调单个算法，而是把感知、定位、规划、控制、仿真、日志和实机问题排查串成闭环，这正是水下机器人系统落地需要的能力。

## 3. 把哨兵项目翻译成水下岗位语言

### 3.1 多源融合定位

当前项目：

```text
/livox/lidar + /livox/imu
  -> Point-LIO
  -> /aft_mapped_to_init, /cloud_registered
  -> loam_interface
  -> small_gicp_relocalization
  -> map -> odom
  -> Nav2 / BehaviorTree
```

水下类比：

```text
Camera + IMU + DVL + USBL + depth + RTK(surface)
  -> VIO / DVL-INS / USBL absolute update
  -> ESKF / factor graph
  -> map/local frame pose
  -> AUV/ROV navigation and control
```

面试可以这样说：

我在项目中实际处理的是 LiDAR-IMU 和点云地图的融合定位。迁移到水下时，我会把 DVL 看作速度观测，把 USBL/RTK 看作低频绝对位置观测，把深度计看作 z 方向强约束，把视觉/VIO 看作相对位姿观测。滤波框架上可以用 ESKF 做在线融合，也可以用因子图做后端优化。关键点不是传感器名字，而是观测模型、噪声建模、时间同步、外参、异常剔除和退化检测。

### 3.2 弱观测和异常处理

当前项目遇到的问题：

1. 高速运动导致局部控制输入变化快。
2. 走廊、墙边、近障碍区域导致点云匹配退化。
3. 视觉跟随目标可能短时丢失或跳变。
4. 重定位失败会影响 `map -> odom`，进而影响规划。
5. 代价地图和真实可通行区域不一致时，MPPI 会表现出抖动或保守。

水下对应问题：

1. 弱纹理、浑浊、低照度导致视觉前端不稳定。
2. DVL 在离底过高或底质复杂时可能失锁。
3. USBL 频率低、延迟大、噪声和跳点明显。
4. 水流扰动导致模型预测和真实运动不一致。
5. 光学目标检测会受浮游物、色偏、散射和运动模糊影响。

面试可以这样说：

我会把水下系统设计成多级可信度融合：每个传感器不只输出数据，还要输出质量指标，例如视觉跟踪内点数、重投影误差、DVL bottom lock、USBL 残差、IMU 饱和状态等。滤波更新时根据质量动态调节观测协方差，严重异常时做 gating 或延迟更新。项目里我已经在点云重定位、视觉目标有效性判断、恢复行为和速度治理里做过类似的工程化处理。

### 3.3 感知到导航控制闭环

当前项目链路：

```text
terrain_analysis_ext
  -> traversability_grid
  -> TraversabilityEsdfProvider
  -> Nav2BSplineSmoother
  -> MPPI
  -> trajectory_speed_governor
```

水下类比：

```text
underwater image / sonar / point cloud
  -> obstacle or target confidence map
  -> local traversability / risk field
  -> path smoothing / local planner
  -> thruster or chassis controller
```

面试可以这样说：

我比较重视感知结果如何被下游稳定消费。项目中不是只把障碍点云发出来，而是进一步转成 traversability grid 和 ESDF，让平滑器知道离障碍的距离梯度，再让 MPPI 在局部控制中稳定跟踪。水下项目里我也会避免感知模块只输出孤立检测框，而是根据任务需要输出目标状态、置信度、可通行区域或风险场，让导航和控制模块能连续使用。

## 4. 高频面试问答

### Q1：你没有水下机器人经历，为什么认为自己适合这个岗位？

我会先承认项目平台不同。我过去做的是陆上高速机器人，不是水下 ROV/AUV。但岗位核心能力并不只取决于平台，而是多传感器融合定位、视觉感知、ROS2 工程化和实机问题闭环。

我的项目里已经完整经历过传感器接入、外参和 TF、LiDAR-IMU 里程计、scan-to-map 重定位、路径规划、局部控制、仿真和实机调参。水下系统把传感器换成 Camera、IMU、DVL、USBL、深度计后，核心仍然是观测模型、状态估计、异常剔除、时序同步和导航控制接口。我缺的是水下传感器的实际调参经验，但我的学习切入点很明确：先从 ROS 驱动和数据格式入手，再建立 DVL/USBL/深度计的观测模型，最后在 ESKF 或因子图中完成融合和调参。

### Q2：如果让你设计一套水下定位融合系统，你会怎么做？

我会先定义状态量，例如位置、姿态、速度、IMU bias，必要时加入水流扰动或传感器外参。预测端用 IMU 做高频传播；DVL 提供机体系速度或对地速度观测；深度计提供 z 方向约束；USBL 提供低频绝对位置观测；视觉/VIO 提供相对位姿或视觉里程计约束；水面 RTK 可以在上浮或水面阶段校正全局坐标。

在线系统可以先用 ESKF，因为实时性好、实现清晰、便于嵌入式部署。复杂任务或离线优化可以用因子图，把 IMU 预积分、DVL、USBL、深度计、视觉重投影或相对位姿都建成因子。工程上我会特别关注时间戳、外参、延迟补偿、观测质量 gating 和坐标系定义。

### Q3：DVL、USBL、IMU 在滤波器里分别是什么角色？

IMU 是高频预测源，负责短时间连续性，但会随 bias 漂移。DVL 是速度观测，通常能显著抑制水平速度和位置漂移，但需要处理 bottom lock 失效、离底高度和安装外参。USBL 是低频绝对位置观测，可以校正长期漂移，但有延迟、跳点和噪声较大的问题。深度计通常是 z 方向很强的观测，可以显著约束深度漂移。

所以我不会简单地把所有数据直接融合，而是会根据观测质量决定是否更新、如何调协方差、是否做延迟补偿。

### Q4：VIO 在水下为什么难？你会怎么增强鲁棒性？

水下 VIO 难在图像质量：低照度、色偏、散射、悬浮物、运动模糊、弱纹理和动态目标都会影响特征跟踪。工程上我会从三个层面处理：

1. 图像预处理：白平衡、颜色校正、CLAHE、去雾/去散射、降噪和畸变矫正。
2. 前端鲁棒性：特征质量筛选、RANSAC、光流跟踪、动态点剔除、关键帧策略。
3. 后端融合：视觉退化时提高视觉观测协方差，更多依赖 IMU/DVL/深度计；视觉恢复后再逐步增加权重。

我现在项目中没有完整落地 VIO，但做过相机模型、PnP 接口、视觉目标有效性判断和视觉结果到导航目标的融合。对 VINS-Mono/Fusion、MSCKF、滑窗优化和 IMU 预积分的原理我可以继续深入，并且能从工程接口开始快速接入。

### Q5：Point-LIO 和水下 VIO/声学融合有什么可迁移之处？

Point-LIO 给我的最大经验是：高频惯性预测加低频或异步外部观测更新。它使用 iEKF 把 IMU 传播和 LiDAR 点到面的残差结合起来，解决高速运动下的连续定位问题。

迁移到水下时，LiDAR 点到面残差可以换成视觉重投影残差、DVL 速度残差、USBL 位置残差或深度残差。虽然观测形式不同，但滤波器关心的是同一件事：状态如何预测、观测如何建模、残差如何构造、协方差如何设置、异常观测如何剔除。

### Q6：你如何处理传感器时间同步？

我会分三层处理：

1. 硬件层：能硬同步就优先硬同步，例如 PPS、触发线、统一时钟源。
2. 驱动层：保证 ROS header stamp 使用采样时间而不是接收时间，记录设备时间和主机时间偏差。
3. 算法层：低频传感器做插值或延迟补偿，高频 IMU 用 buffer 按观测时间积分到目标时刻。

项目中我经常通过 TF lookup、话题频率、时间戳和 rosbag 回放排查导航抖动。水下系统里 USBL 延迟更明显，所以我会把延迟建模为系统参数，必要时使用 fixed-lag smoother 或延迟状态更新。

### Q7：你如何做相机标定和外参标定？

相机内参方面，我会用棋盘格/AprilTag 标定焦距、主点、畸变参数，并在图像进入检测或 VIO 前做去畸变。外参方面，根据传感器组合选择手眼标定、Kalibr、PnP 标定或基于运动约束的联合优化。工程落地时，外参必须进入 TF 树或参数文件，并且要通过重投影误差、静态姿态检查和动态轨迹一致性验证。

项目中我已经接触过相机内参接口、`solvePnP`、相机与云台/底盘 TF，以及 LiDAR/IMU 安装外参配置。面试中可以强调：我知道标定不是一次性工作，而是会影响定位残差、控制稳定性和长期漂移。

### Q8：如果水下目标检测出现漏检和误检，你怎么处理？

我会先区分数据问题、模型问题和系统问题：

1. 数据问题：光照、浑浊、色偏、运动模糊、目标尺度变化是否覆盖在训练集里。
2. 模型问题：检测阈值、类别混淆、增强策略、输入分辨率、部署精度是否合适。
3. 系统问题：单帧检测是否需要跟踪器、是否融合 IMU/深度/声学先验、是否有任务层 gating。

我的项目里视觉跟随不是看到一帧目标就直接控制，而是通过有效性判断、目标平滑、行为树门控和 Nav2 目标生成来避免抖动。水下目标检测也应类似处理：检测框只是前端观测，最终要进入状态跟踪和任务决策。

### Q9：你怎么证明一个定位算法稳定？

我会从指标和场景两方面证明。

指标上看：绝对轨迹误差、相对轨迹误差、漂移率、重定位成功率、观测残差分布、TF 连续性、CPU 占用、端到端延迟。没有真值时，可以用闭环误差、重复航线一致性、地图对齐误差和任务成功率。

场景上看：正常巡航、急转、低纹理、动态干扰、传感器短时失效、低频绝对观测跳点、长时间运行和重启恢复。

项目中我会通过 RViz、rosbag、TF、轨迹话题、costmap、ESDF 可视化和仿真复现来定位问题。水下项目里我也会保留同样的调试闭环。

### Q10：如果上船/下水测试时定位突然发散，你会怎么排查？

我会按链路从前到后排查：

1. 原始传感器：IMU 是否饱和，DVL 是否 bottom lock，USBL 是否跳点，图像是否过暗或模糊。
2. 时间和外参：时间戳是否错位，TF 是否断连，外参方向是否写反。
3. 算法残差：滤波创新是否异常，协方差是否过小，gating 是否失效。
4. 坐标系：ENU/NED、机体系方向、深度正方向和控制坐标是否一致。
5. 下游影响：导航是否继续使用了不可信定位，是否需要触发降级或悬停。

我会优先保住系统安全：定位置信度低时让控制进入限速、悬停或人工接管，而不是继续执行高风险路径。

## 5. 面试可重点展开的项目亮点

### 5.1 LiDAR-IMU + GICP 的分层定位

可以讲：

项目没有把所有定位压力放在一个模块上，而是分成局部连续里程计和全局地图修正。Point-LIO 负责短时间高频连续性，small_gicp 负责低频全局校正。这种结构和水下 DVL/IMU + USBL/视觉回环的分层思路很像。

### 5.2 traversability grid 到 ESDF 的安全约束

可以讲：

我把地形感知输出从点云进一步整理成可通行栅格，再构造 ESDF，让轨迹平滑器可以根据障碍距离做连续优化。这个经验可以迁移到水下局部避障，比如把视觉/声呐感知结果转成局部风险场，给路径平滑或 MPC 使用。

### 5.3 行为树管理复杂任务

可以讲：

项目通过 BehaviorTree.CPP 管理巡逻、视觉接管、资源状态、受击恢复等任务切换。水下任务也有类似需求，比如巡航、目标搜索、抵近检测、失联返航、低电量上浮、定位异常悬停。行为树能把算法状态和任务逻辑解耦，便于测试和维护。

### 5.4 Gazebo + loopback 双层仿真

可以讲：

我在项目里既使用轻量 loopback 快速验证导航闭环，也接入 Gazebo 验证传感器和环境交互。水下项目也可以采用类似策略：先用轻量运动学仿真测算法逻辑，再用 Gazebo/UUV Simulator 或真实 rosbag 做传感器级验证，最后进水池和海试。

### 5.5 实机问题闭环能力

可以讲：

我习惯从话题、TF、参数、日志、RViz、rosbag 和代码落点一起排查问题。比如导航不动时，不只看 MPPI，还会向上查行为树是否持续下发目标，定位是否稳定，costmap 是否被错误障碍占满，速度平滑和坐标转换是否压掉了速度。水下机器人更依赖这种系统级排查能力。

## 6. 不要踩的坑

### 6.1 不要说自己做过真实水下项目

推荐说法：

我没有真实 ROV/AUV 水池或海试经验，但我做过完整 ROS2 移动机器人定位导航系统。我的优势是能把多传感器融合、状态估计、导航控制和实机调试串起来，水下传感器模型我会补齐，并且可以从 DVL/USBL/深度计观测模型和数据回放开始快速上手。

### 6.2 不要把视觉项目夸成完整 VIO

推荐说法：

我项目中的视觉更多承担目标检测/跟随和导航目标生成，不是完整 VIO。但我理解 VIO 的核心链路：特征跟踪、PnP/对极几何、IMU 预积分、滑窗优化、重投影误差和边缘化。我的工程基础包括相机模型、PnP、TF 融合和视觉目标稳定性处理。

### 6.3 不要只讲算法名

面试官更关心你是否能落地。每个算法都要讲清楚：

1. 输入是什么。
2. 输出是什么。
3. 在系统里解决什么问题。
4. 失败时怎么发现。
5. 参数怎么调。
6. 如何影响下游导航控制。

## 8. 30 秒结尾总结

我的项目背景是陆上 RoboMaster 哨兵机器人，但我做的不是单点算法，而是完整机器人系统：传感器接入、融合定位、重定位、可通行性建模、轨迹优化、局部控制、行为树、仿真和实机排障。水下岗位的传感器会变化，环境也更困难，但底层工程能力是一致的：把不完美的多源观测稳定融合成可靠状态，再让感知、导航和控制闭环工作。我希望在这个岗位上补齐水下 DVL/USBL/深度计和水下视觉的实际经验，同时把我已有的 ROS2、状态估计和系统调试能力快速投入到项目里。
